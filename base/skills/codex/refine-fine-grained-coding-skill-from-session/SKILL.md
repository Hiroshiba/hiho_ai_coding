# きめ細やかな実装スキルを、指定セッションの指摘から改善する

## 目的

指定された Codex のきめ細やかな実装依頼セッションを読み、既存のきめ細やかな実装用スキルを改善する。

改善後のスキルは、機能やバグ修正の目的を満たすだけでなく、既存コードになじませ、ユーザー本人の意図・好み・明示された優先順位に従って実装するためのものとする。一般的な「よい実装」の説明を増やすのではなく、このユーザーの代わりに実装するうえで不足していた判断材料を補う。

この作業の対象は実装用スキルであり、ログに登場するプロダクトコードの修正や、新しいコードレビューではない。

ログの取得には既存の専用コマンドを使う。対象スキルの更新には Codex 公式の `$skill-creator` を使う。

## 1. 指摘と、その判断に必要な文脈を読む

対象スキルと関係する既存の参照資料を読み、すでにある判断基準を把握する。

対象セッションでは、指摘文だけでなく、元の依頼、Codex が提案・実施した変更、ユーザーの指摘、その後の修正と結果を関連づけて読む。何が不足し、何を知っていればその指摘を防げたかを調べる。

必要に応じて、ログで参照された既存コード、類似実装、呼び出し元・呼び出し先、テスト、関連ドキュメントを確認する。調査範囲は指摘の解釈に必要な範囲に絞る。

ユーザーの発言、コードから確認できる事実、Codex による解釈を混同しない。候補となる学びには、根拠となるセッション内の箇所と、必要なコード参照を対応づける。確認できないことは不明として扱う。

## 2. 将来の実装を変える学びを取り出す

次の観点で、実際に指摘された内容と、それを解消した判断を取り出す。すべての観点を埋める必要はない。

### 既存実装との整合性

既存の責務分担、処理の配置、呼び出し関係、命名、実装パターンを踏まえられていたか。既存の仕組みを見落としたのか、見つけたが使い方を誤ったのか。変更部分だけでは分からない関連箇所との関係があったか。

### ユーザーの意図と好み

ユーザーが実現したかった振る舞い、避けたかった実装、好んだ説明やコードの表現は何か。ユーザーが複数の方針から選んだものや、何を優先するよう明示したかを取り出す。

### 変更内容と範囲

何を変更すべきで、何が今回の目的に不要だったか。機能変更に別の整理を混ぜたこと、必要な関連変更を落としたこと、不要な複雑さを持ち込んだことについて指摘があったか。

### テスト・コメント・ドキュメント

どの振る舞いを確認すべきだったか。テストが何を保証すべきか。コメントやドキュメントには何を説明し、どの既存用語や表現に合わせるべきだったか。

事実、ユーザーの好み、再利用できる実装手順を分けて整理する。失敗だけでなく、ユーザーが明確によいと評価した対応も材料にする。

## 3. 指摘を、具体的で適用範囲のある規則へ変換する

採用候補は、次の内容が読み取れる短い規則にする。機械的に全項目を見出し化する必要はない。

- 適用条件：どの種類の変更・コード・状況で使うか。
- 実行する行為：何を確認し、どのように判断・実装するか。
- 理由：どの見落としや手戻りを防ぐか。
- 具体例または参照先：理解に必要な実例、既存実装、根拠となる指摘。
- 確認方法：その規則を守れたことを、何で判断できるか。

「既存コードに合わせる」「意図を尊重する」「適切に実装する」で終わらせず、何に合わせ、何を確認し、行動をどう変えるかまで書く。

禁止事項を残す場合は、代わりに取るべき行為も示す。プロジェクトや特定の部分に限られる知識を、ユーザーの全プロジェクトに適用する規則へ広げない。ユーザーの好みの内容を、一般的なベストプラクティスで置き換えない。

コードの内容を長く複製せず、必要な参照先を残す。コードに依存する知識は、次の実装で適用する際に、その参照先と現在のコードの整合性を確認できるようにする。

## 4. 有用な内容だけを、既存スキルへ統合する

モデルが通常すでにできる一般論、今回限りの作業記録、再利用性のない細部、根拠の確認できない解釈を規則として追加しない。一方、その一件から再利用できる判断が得られるなら、出現回数だけを理由に除外しない。

既存スキルに同じ内容がある場合は重複追加しない。曖昧さ、不足する適用条件、古くなった参照先など、必要な箇所を改善する。新旧の内容が矛盾する場合は根拠と適用範囲を調べ、解消できない部分を断定的に統合しない。

有効な既存規則や構成を維持し、必要な箇所を局所的に更新する。短くするために、判断に必要な条件や例を消してはならない。実装時に読む判断基準と、改善の根拠となる詳細な記録は区別する。

## 5. 改善内容に対応する確認材料を用意する

対象の指摘をもとに、変更後のスキルで期待する判断と、避けるべき判断を具体化する。機能が動くかだけでなく、指摘された既存実装との整合性やユーザーの好みを満たすかも確認対象にする。

利用可能な過去の確認材料があれば、今回の改善によって従来できていた判断を壊さないことも確認する。評価は一般的なコードの好みではなく、元の依頼とユーザーの指摘に基づける。

改善する箇所、規則、根拠、確認材料を `$skill-creator` に渡して、対象スキルへ反映する。意味のある改善が見つからなければ、無理に変更しない。

## 完了時の報告

更新したスキルと箇所、追加・修正・統合した判断基準、その根拠と期待する行動の変化を報告する。重要な保留・不採用項目があれば理由を添える。

確認できたことと未検証のことを分ける。文面を点検しただけの場合に、実際の Codex の実装品質が改善したとは報告しない。
