### 最終結果ではなく操作と待機の順序を比べる

最初の依頼ログ9行の目的は、最終的に同じアプリとエンジンが導入されることだけではない。
利用者が選択した後に長く待ち、さらにクリックして再び待つ流れをなくすことまで含む。

対象ログ3664行で比較した二つの経路は、最終状態は同じでも操作順が異なる。
従来経路への統一はビルド差分を減らすが、待機後の操作を復活させるため不採用になった。
行数、ファイル数、最終状態だけを合格条件にすると、元の課題を再発させる。

待機や操作の削減を扱う場合は、各経路について操作、待機、画面遷移、自動処理の順序を書き出す。
長い待機の前後のどちらに操作があるかも区別する。
同じ回数の操作でも、待機後に利用者を呼び戻す操作は別の負担になる。

### フック全体とモード固有処理の条件を分ける

フォーク元ログ1902行では、同梱版だけに `afterAllArtifactBuild` を登録する案が途中案として示された。
対象ログ2124行で利用者は、インストーラーモードによってフック全体の有無を切り替えるのは責務に合わないと判断し、フックは常に登録して、分割だけを同梱版の条件にするよう求めた。
2420行の報告と現在の [electronBuilderConfig.ts](/home/hihok/Github/voicevox/hiho_git_worktrees/standard-assisted-auto-engine/build/electronBuilderConfig.ts) 126行、[afterAllArtifactBuild.ts](/home/hihok/Github/voicevox/hiho_git_worktrees/standard-assisted-auto-engine/build/afterAllArtifactBuild.ts) 11行から18行で、この分担への変更を確認できる。

フックの一部だけがモード固有なら、登録の有無でフック全体を消さず、該当処理の直前で条件を判定する案を基準にする。
これにより、フック名が表すライフサイクル責務と、分割など個別処理の適用条件を分けられる。
フック全体が実際にそのモード専用なら、登録側で分ける案も成立するため、常時登録を一律の規則にはしない。

### 要素内の順序と全要素の同期点を分ける

- 対象ログ2583行で、利用者は現在情報を画面へ反映した後に最新情報を取得する既存順序が失われていないか確認した。
- 2629行でCodexは、各エンジンについて現在情報の後に最新情報を取得しているため順序は維持されていると回答した。
- 2721行で利用者は、確認したかったのは各エンジン内の順序だけでなく、全エンジンの現在情報を取得した後に全エンジンの最新情報を取得する同期点ではないかと指摘した。
- 2783行の再調査では、デフォルトブランチも全体の同期点を持たず、エンジンごとに現在情報が終わり次第、最新情報へ進むことが確認された。挙動変更は不要と判断された。

現在の [store/index.ts](/home/hihok/Github/voicevox/hiho_git_worktrees/standard-assisted-auto-engine/src/welcome/store/index.ts) 218行から223行も、各要素内の順序だけを保証する。
この形では、エンジンAの最新情報取得がエンジンBの現在情報取得より先に始まり得る。
二段の `Promise.all` なら、全要素の現在情報が完了するまで最新情報を開始しない。

順序を説明または変更するときは、要素内の先行関係と、要素間の同期点を別々に図示する。
画面へ途中結果を出す目的も、各要素の現在情報を順次表示できれば足りるのか、全要素を同じ段階までそろえる必要があるのかで実装が変わる。
どちらを選ぶかは目的と既存挙動から決め、`Promise.all`を使うかどうかだけでは決めない。
