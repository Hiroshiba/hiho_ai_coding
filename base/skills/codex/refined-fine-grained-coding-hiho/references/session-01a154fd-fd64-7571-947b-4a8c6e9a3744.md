## 統合する判断基準と、その範囲

既存の用語衝突や背景説明の規則を維持し、関連文書の編集時に読む「手順書と更新情報を、用途ごとの既存例へ合わせる」を追加する。

- 手順書では、共通部分と更新種別による違いを対応付ける。調査観点や自動で完了する処理を毎回の独立項目へ足す前に必要性を確かめ、操作名、条件、補足の粒度を既存例へ合わせる。条件は一つの発生契機だけで狭めず、作業が必要になる状態から決める。
- 更新情報は、掲載先ごとの過去版から採否と定型を調べる。候補の実際の変更前後と影響範囲も確認し、コミット名や技術的な重要度だけで掲載を決めない。更新情報JSONの定型とGitHub Releaseの主要項目を分けて選ぶ。
- 公開APIの呼称はREADMEと文書生成元のコード、修飾語は掲載先の過去例へ照合する。関連製品との文面一致を指定された変更には、その既存文面を使う。

周囲との一致、過去版と公開APIの説明の確認、掲載先ごとの採否を分けることは、上記のユーザー発言に根拠があり、証拠があってそうすべきである。
これらを別の関連文書でも使える確認手順へまとめることは、そうすべきだと思うという判断である。特定のリリースで採用した項目数、語句、ブランチ操作を全案件へ固定する根拠にはしない。
