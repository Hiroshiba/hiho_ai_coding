# 既存の処理関係から実装の細部を決める

## 変更の目的を、省略経路まで含む合格条件に置き換える

処理の一部更新・移行・再利用を実装する場合は、作業前に、変更する結果と変えてはいけない結果について、比較する入力、期待する値、観測する箇所を定めよ。呼び出し削減が目的なら、呼び出し数と、無関係な判定や通知を変えないことを別々に確認せよ。
確認対象は利用者の例だけで決めず、通常の入口から分岐を追え。一部更新、失敗・延期、外部呼び出しだけの省略、解析全体の省略、保存後の再利用のうち、目的に関係する経路ごとに、更新する値・保持する値・下流へ渡す値を対応付けよ。

保持を確認する対象は、移行後に残った値や既知の不具合例だけから選ばず、変更前に利用されていた値から洗い出せ。対象自身の本文だけで入力不変と判断せず、判定が依存する関連候補や確定情報も照合し、正当な更新・取消と適用漏れを分けよ。
許可された実データのコピーを、本番と同じ正規化・識別子付与・対象選別・入力生成に通し、利用先の判定から保存・再読込まで合格条件を照合せよ。手作りの中間入力で失敗した場合は、本番の生成経路でも成立する入力か確かめてから修正の根拠にせよ。
型検査、保存値の存在、処理の正常終了だけで保持を保証するな。確認した入力と経路、実際に比較した判定や通知候補、未確認の経路を分けて報告せよ。

## 型と関数を、使われ方と周囲の粒度に合わせる

型だけのファイルを作る・維持する場合は、型の利用先と責務を調べよ。一つの処理の引数契約を呼び出し側も参照しているだけなら、複数ファイルから使うという理由だけで独立させず、その処理のモジュールへ置けるか確かめよ。移動で実行時の依存や循環参照を増やさないことも確認せよ。
直和型で同じ付随データを持つ選択肢は、分岐ごとの違いが識別値だけなら、その識別値をまとめてデータの定義を一度にせよ。例えば `{ mode: "none" } | { mode: "copy" | "move"; directory: string }` とし、利用側で必要な絞り込みが働くか確認せよ。

追加・変更した関数の配置、戻り値注釈、docstringの句点は、同種の既存関数と照合せよ。新設したファイル内の自分の書き方だけを前例にせず、既存ファイルの補助関数とdefault exportの位置、省略可能な `void` の扱いを調べよ。
短いオブジェクト・型・関数呼び出しは、周囲に合わせ、フォーマッターが保つなら一行にまとめよ。既存との差分に不要な空行や複数行化が混ざっていないか確認し、フォーマッターの制約を回避するための設定変更はしない。

一つの概念の名前を直す場合は、型、生成する関数、使う関数、変数、外部設定名、docstringを呼び出し経路に沿って照合せよ。配置元だけでなく方法も含む型を `Source` と呼ぶなど、名前が扱う範囲を狭く見せていないか確認せよ。
値の有無を調べる名前は実在確認と区別し、パスを組み立てて返す関数は、同種の既存関数の動詞に合わせよ。コピー元・コピー先を表す `source`・`destination` など、別の役割を正しく表す名前まで機械的に置き換えるな。docstringにも関数の目的を超える自明な説明を足さない。

## 入力の補完・検証・変換を分けて簡潔にする

複数の入力から動作を決める処理を簡略化する場合は、未指定、空文字、有効値、不正値の組合せについて、受理・拒否と返す値を先に整理せよ。維持する条件と変更してよい条件を区別し、過去のフォールバックや出力形をすべて保つ前提だけで「これ以上簡単にできない」と結論するな。
既定値が必要だと説明するときは、必要な振る舞いと特定APIの必要性を分けよ。明示値では成功し、未指定時だけ失敗するなら、その最小の入力例を示せ。分岐の順序やライブラリ機能で解決するかは、採用版の文書・実装と、その入力の結果から判断せよ。

短い検証関数で条件の関係が読みにくい場合は、未指定値の補完を先に済ませ、許される組合せを同じ形の分岐で並べよ。前の分岐の否定を読み解かないと次の正常条件が分からない構造を避け、数行の削減よりも条件を直接読めることを優先せよ。
Zodへ集約する案では、既存関数を長い `transform` へ移しただけで簡潔になったとみなすな。許される組合せをobjectのunionで表せるか、検証と値の変換を分けられるかを確かめよ。型をスキーマから導出する場合は、別の手書き型を維持せず、不要なプロパティの除去とリテラル型の絞り込みも確認せよ。
検証済みの値から型付きオブジェクトを作り、同じ実行内で直接渡す箇所では、再検証が新たに防ぐ不正入力を特定せよ。型を置くためだけのスキーマや重複したparseを増やさず、検証は必要な入力境界へ置け。これは外部入力の初回検証や、保存・通信を経た値の再検証を省く指示ではない。

保存済みの採用値を再利用・移行する場合は、新規出力に必要な条件と、過去の採用を確認する条件を分けよ。新規AI出力の件数上限や根拠分類を、集約済みの保存値へそのまま課して切り捨てるな。旧処理での採用条件と照合し、保存・再読込でも根拠や信頼度が変わらないか確かめよ。
過去の判定をAIへ固定値として渡す場合は、保存する値と根拠を保ち、今回の入力に必要な情報だけを投影せよ。新しい出力には現在の根拠を要求し、過去の根拠が現在の取得範囲にないという理由だけで再利用を止めたり、無関係な再取得・再推論を増やしたりしない。呼び出し不要と決まる前の入力準備にも、新規生成専用の条件が残っていないか追え。

## 採用値の移行と再利用を、使う側までつなぐ

採用済み判定の移行対象は、最終状態の分類名だけで絞らず、旧処理が何を判断材料として使ったかから決めよ。AIの直接出力に加え、その解釈を規則へ渡して得た値と下流の関係について、採用を裏付ける保存値を対応付けよ。候補が保存されているだけで採用済みとせず、新しく採用された結果や明示的な取消を古い候補で上書きするな。

処理を省く分岐のreturnやcontinueを調べ、生成だけを省くのか、結果の適用まで省くのかを区別せよ。保持するオブジェクトが残っていても、後続の引数や集約配列に入らなければ使われない。AIだけを呼ばない分岐と、解析対象から外れる分岐の両方で、採用値が通常の適用処理を経て、グラフや通知などの利用先へ届くことを確かめよ。
生成結果がないことを、採用済みの関係なしや取消として解釈させるな。復元時の信頼度や派生値も通常の計算処理に通せ。保存する採用値に加え、待ち相手・次の行動・通知候補も、比較する入力に対して期待した結果になるか確認せよ。
保持・取消は項目全体の成功・延期だけで決めず、要素ごとの必要性、新しい採用、確定情報による不要化から判断せよ。例えば、項目全体が延期でも、終了済みという確定情報で不要になった待ち相手を復活させない。

省略・移行・入力生成の判断を具体例で確認する場合は、[採用値の保持と利用経路に関する指摘と確認材料](references/session-01a07bc9-31a9-7f10-81ec-eee5b5302a80.md)を参照せよ。

## ビルドの補助処理は、導入理由と現在の成果物から判断する

権限復旧や空ディレクトリ作成を移す・削除する場合は、元々何が失われるために必要だったかと、その受け渡し工程が今も通るかを追え。
採用版の配布アーカイブに必要な権限・ディレクトリがあること、展開・改名・言語削除などを経ても保持されること、後続の成果物受け渡しで再び失われないことを対応付けよ。最新版の説明や「昔からある」だけで残す・消すを決めない。
アプリ本体・Helperと、別途取得する同梱エンジンでは生成・配置経路が異なる。一方で不要だったchmodを、他方でも不要とみなさず、各対象の経路で判断せよ。コードとアーカイブの確認、配布用ビルド、起動確認の実施範囲を分けて報告せよ。

ビルド処理で実行ファイル名を使う場合は、表示用製品名、パッケージ名、OS別の実行ファイル名の生成元を照合せよ。CIの明示設定でたまたま同じ値になることを保証にせず、未指定時の実ファイル名と処理対象も一致するか確認せよ。

## 設定と配置の変更を、後続の利用側まで追う

環境変数の既定値や必須条件を変える場合は、workflow・job・stepの定義と引き継ぎを調べ、初回ビルド、同梱しない構成、後続の再パッケージで実際に渡る値を照合せよ。処理本体を省く経路でも、設定ファイルの読み込み時に検証されないか確かめよ。
後続stepで空文字に上書きする必要が生じたら、共通定義を残す前提と、必要なstepだけに渡す案を分けて判断せよ。既定値や設定の範囲を変えてよいと決まったら、補完処理だけでなく入力元もそろえ、不要になった回避策を残さない。

成果物の配置を共通処理へ移す場合は、CIとローカルの各経路について、変更前後の配置先と、起動側が解釈する相対パスの基準を対応付けよ。一つの経路だけ変わるなら、その条件を示し、「保存先は変わらない」「ローカルでは動かない」と全体へ広げるな。
既存の配置先が経路ごとに違う場合は、参照する設定と導入時の議論を確認し、残ったコードだけから正しい配置を決めない。変更されなかった事実と、残した意図が記録されているかは区別せよ。

型・入力条件・ビルド経路の判断を具体例で確認する場合は、[実装の細部に関する指摘と確認材料](references/session-01a07896-34af-7d52-bf96-6059e7ac962b.md)を参照せよ。

## 設定の順序は選択と呼び出しの両方から決める

複数のプラグインが同じ処理の入口を提供し、設定順を変える場合は、採用版の実装から、どの入口が選ばれるかと、選ばれた実装が他のどの処理を呼ぶかを別々に追え。
「後のものが選ばれる」と分かっただけで調査を終えず、その入口を選ぶと必要な処理がそろう理由と、逆の組合せでも同じ処理が呼ばれるかを確かめよ。
各プラグインが自分を最後に置くよう説明している場合も、併用への対応と呼び出しの向きを採用版で照合して順序を決めよ。
「最後に置く」という現在の配置を、無関係な入口を提供するプラグインも含む恒久的な制約へ広げるな。別の実装が必要な処理をまとめて呼ぶようになれば、順序を見直す条件になる。

整形プラグインの順序を直す場合は、問題の整列と併用する整列の両方が必要な未整形の入力を使い、既存の実行経路で両方の出力を確かめよ。
整列処理が呼ばれない設定でもチェックが成功する場合があるため、チェックの終了コードだけで有効化を判断するな。変更前後の実際の整列結果と、整形後のチェックを対応させよ。

## コメントに制約が必要になる理由を残す

コードだけでは読み取れない配置や設定の制約を説明する場合は、守りたい結果に加え、その配置が必要になる処理の関係を書け。
「互換性を保つため」のような目的だけでも、「最後のパーサーが選ばれるため」のような選択の仕組みだけでも足りない。なぜその実装に任せるのかを、実際に呼ばれる処理に結び付けよ。
現在の項目名や配置の繰り返しを理由にせず、併用相手や呼び出し関係が変わったときに制約を見直せる説明にせよ。

理由を短いコメントへまとめるときは、調査で使った内部用語をそのまま残さず、対象の実装が何を実行するかを動詞で示せ。
周辺コードとコメントだけを読んで、何を任せ、そのためにどう配置するのかがつながるか確かめよ。専門用語の置き換えや文章 lint の通過だけでは、意味が伝わったことにならない。

## 説明は変更判断をする箇所に置く

コメントを記せる設定ファイルでは、特定の項目の順序や値を守る理由を、設定を変更する人が読む該当箇所へ置け。この理由を README の一般的な操作手順へ分離しない。
一項目だけにかかる短いコメントは、直前の独立行だと「これ以降」への説明に見える場合、該当項目の行末に置け。複数項目に共通する説明は、そのまとまりに対応する位置を選べ。
これは必要な理由コメントの配置基準であり、自明な設定にもコメントを増やす指示ではない。

順序制約やコメントの判断を具体例で確認する場合は、[指摘の根拠と確認材料](references/session-01a07ce4-7270-7b32-8820-ecfa7b206d96.md)を参照せよ。
