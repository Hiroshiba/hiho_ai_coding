# Codex の設計セッションから設計スキルを改善する

## 目的

指定された設計依頼セッションを、既存の設計用スキルを改善するための証拠として分析せよ。

単に指摘を列挙するのではなく、次を明らかにせよ。

1. どの設計判断、欠落、曖昧さが指摘につながったか。
2. 何が問題で、どのような影響または手戻りを生んだか。
3. セッション内で、最終的にどの修正方針が受け入れられたか。
4. 将来の別の設計依頼でも役立つ形に、どの規則を一般化できるか。
5. 改善後の設計用スキルが、同じ失敗を事前に防げるか。

人物を評価したり責めたりせず、設計プロセス、判断基準、成果物の不足を改善対象にせよ。

## 既存機能

- セッションログの取得には `Hiroshiba/hiho_scripts` の `get_codex_session_jsonl_paths.py` を使用する。詳細は `hiho_get_codex_session_jsonl_paths -h` を実行する。
- 設計用スキルの作成・更新は Codex 公式の `$skill-creator` を使え。

## 必須入力

- 対象の Codex セッションを一意に特定できる情報
- `~/Github/hiho_ai_coding/base/skills/codex/refined-codedesign-hiho/SKILL.md`

## 作業範囲

このスキルが行うのは、ログ分析、改善案の選別、設計用スキルの更新、更新結果の検証だけである。

次は行うな。

- 対象プロダクトやコードの実装
- ログ取得方法の再実装または説明
- `$skill-creator` と同じ機能の再実装または説明
- 指定されていないセッション、リポジトリ、課題の調査
- 明示された目的や非目標を越える機能追加
- 一度きりのプロジェクト事情を、一般的な設計原則として無条件に追加すること

## 手順

### 1. 現在の設計用スキルを把握する

改善対象の `SKILL.md` と、そこから直接参照される関連資料を読め。

次を把握せよ。

- スキルの対象範囲と対象外
- 現在の設計手順
- 現在要求している設計成果物
- 既存の確認項目と判断基準
- すでに同じ内容を扱っている規則
- スキルの説明文が想定している起動条件

既存規則と重複する改善案を、そのまま追記してはならない。

### 2. 指定セッションを時系列で読む

既存の専用コマンドで対象ログのパスを得て、指定セッションの全体を時系列で読め。

一部の指摘だけを抜き出さず、少なくとも次の流れを復元せよ。

1. ユーザーの最初の依頼
2. 目的、要件、制約、非目標、前提
3. Codex が提示した設計または計画
4. ユーザーまたはレビュー担当者からの指摘
5. 指摘を受けた修正
6. 修正に対する追加指摘
7. 最終的に受け入れられた状態、または未解決の状態

ツール実行や中間メモは、設計判断または指摘の理解に必要なものだけを使え。

### 3. 設計に関係する指摘を抽出する

次を設計上の指摘候補として抽出せよ。

- 設計案への明示的な訂正、拒否、追加、削除、方向転換
- 要件、制約、非目標、対象範囲の読み落としに対する指摘
- コンポーネント分割、責務、依存関係、境界、インターフェースへの指摘
- データ、状態、ライフサイクル、正常系、異常系、並行処理への指摘
- 選択肢、根拠、利点、欠点、トレードオフの不足への指摘
- セキュリティ、プライバシー、信頼性、性能、運用などの品質要件への指摘
- 互換性、移行、展開、撤回、廃止、バージョン差への指摘
- テスト可能性、検証方法、監視、障害調査方法への指摘
- 実装または検証の結果によって、設計時の前提や実現可能性が誤っていたと判明したもの
- 同じ点を何度も説明し直しており、設計成果物の曖昧さが原因だと分かるもの

実装への指摘は、次のいずれかを示す場合だけ取り込め。

- 設計上の契約または責務が不足していた
- 必要な状態遷移、データフロー、失敗時の扱いが決まっていなかった
- 技術選定または構造が要件を満たせなかった
- 運用、移行、互換性、セキュリティ、性能、検証可能性を設計で考慮していなかった
- 実装者が合理的に一意に判断できるだけの設計情報がなかった

変数名、整形、局所的なコードスタイル、単発の記述ミスなど、設計判断に結び付かない指摘は取り込むな。

### 4. 証拠の強さを確認する

指摘候補ごとに、次を区別せよ。

- ユーザーまたはレビュー担当者による明示的な指摘
- その後の会話で受け入れられた修正
- 実装、テスト、検証結果による客観的な裏付け
- Codex 自身の推測または自己反省

Codex 自身の推測だけを根拠に、設計用スキルを書き換えるな。

会話中の質問、検討案、迷いを、最終決定として扱うな。最終的に採用されたか、少なくとも明示的に問題として認められたことを確認せよ。

事実と推定を分け、推定にはその根拠を付けよ。

### 5. 設計観点から原因を分析する

指摘を表面的な言い換えで終わらせず、どの設計工程または成果物が不足していたかを分析せよ。

対象の依頼に関係する観点だけを選び、次を確認せよ。すべてを機械的に要求してはならない。

#### 問題設定

- 解くべき問題と利用者への価値
- ステークホルダーと主要ユースケース
- 目標、非目標、成功条件
- 機能要件と品質要件
- 制約、前提、未確定事項
- 既存システムとの関係と変更範囲

#### 構造と振る舞い

- システム境界と外部依存
- コンポーネント、責務、所有権、依存方向
- API、イベント、ファイル形式、永続化形式などの契約
- データの生成元、所有者、保存先、更新、削除、整合性
- 主要な正常系と異常系の時系列
- 状態遷移、再試行、冪等性、競合、並行処理
- 実行環境、配置、権限、外部サービス

#### 判断とトレードオフ

- 検討した代替案
- 採用案と採用理由
- 各案の利点、欠点、制約、影響
- 採用しない案を退けた理由
- 何もしない場合の影響
- 未解決の問いと将来の拡張

#### 品質特性

対象に関係するものについて、具体的なシナリオまたは判定可能な条件で確認せよ。

- 信頼性、可用性、復旧性、データ保全
- セキュリティ、プライバシー、権限、脅威
- 性能、遅延、スループット、資源量、拡張性
- 運用性、可観測性、保守性、変更容易性
- テスト容易性、デバッグ容易性
- コスト、持続可能性
- ユーザビリティ、アクセシビリティ、国際化

#### 導入と進化

- 既存利用者、既存データ、既存 API との互換性
- 移行方法と移行失敗時の扱い
- 段階的な展開、機能の有効化と無効化
- ロールバック条件と手順
- バージョン差、アップグレード、ダウングレード
- 廃止予定、依存関係、運用担当者への影響

#### 検証と運用

- 設計を確かめるテスト、試作、計測
- 受け入れ条件または完了条件
- 主要リスクと緩和策
- 本番で正しく動いていると判断する方法
- 異常を検出する指標、ログ、イベント
- 障害時の診断と復旧方法

### 6. 指摘レコードを作る

各指摘を次の形式で記録せよ。

```text
ID: F-<連番>
根拠: <発言者、時刻またはログ上の位置、短い引用または要約>
当初の設計: <指摘前の判断、欠落、曖昧さ>
指摘内容: <何が問題とされたか>
設計上の原因: <どの工程、判断基準、成果物が不足していたか>
影響: <誤った方向、手戻り、リスク、理解不能など>
受け入れられた修正: <セッション内で採用された修正。なければ未確定>
分類: <問題設定、構造、契約、振る舞い、品質、進化、検証、説明など>
重要度: <Blocker | Major | Minor>
一般化した教訓: <将来の設計依頼にも適用できる内容>
```

重要度は次の基準で付けよ。

- `Blocker`: 明示要件または制約に反する、設計方針自体が成立しない、大幅な作り直しを生む
- `Major`: 重要な品質、契約、運用、移行、検証が欠け、実装後の重大な問題または手戻りにつながる
- `Minor`: 主に説明、構成、用語、局所的な明確さの問題である

重大な設計方針の問題を先に扱え。

### 7. スキル変更案へ変換する

指摘レコードごとに、改善対象の設計用スキルを次のどれにするか決めよ。

- `add`: 新しい確認または手順を加える
- `strengthen`: 既存の弱い規則を具体化する
- `clarify`: 起動条件、適用条件、成果物、判断基準を明確にする
- `reorder`: 重大な問題をより早く検出できる位置へ移す
- `remove`: 誤解を招く、矛盾する、不要になった規則を削除する
- `no-change`: 既存規則で十分、一般化不能、根拠不足などのため変更しない

追加または変更する規則は、可能な限り次の形にせよ。

```text
<適用条件>のとき、<具体的な設計行為>を行え。
成果物には<必要な情報>を明示せよ。
<確認質問または判定条件>で妥当性を確かめよ。
```

「よく考える」「注意する」「適切に設計する」のような、行動と判定方法が分からない表現は禁止する。

各変更案について次を確認せよ。

- セッションの証拠に結び付いている
- 将来の類似依頼でも役立つ
- 既存規則と重複していない
- 他の規則と矛盾しない
- 対象スキルの範囲内である
- 実行可能な命令になっている
- 出力または確認方法が分かる

一つのプロジェクトだけの名称、ファイル、技術、暫定事情は、そのまま一般スキルへ入れるな。対象スキル自体がその領域専用であり、今後も必要な知識である場合だけ、最も狭い適切な場所へ置け。

### 8. 設計用スキルを更新する

変更判断を整理した後、`$skill-creator` を使って改善対象の設計用スキルを更新せよ。

更新時は次を守れ。

- 元のスキルの仕事を広げすぎない
- 既存文を直せる場合は、類似規則を末尾へ追加しない
- 重複、矛盾、古い規則を整理する
- 命令形で、入力、行動、成果物、判定条件を明確にする
- `SKILL.md` には中核の手順だけを残す
- 詳細な領域別資料が本当に必要な場合だけ、参照先へ分離する
- 改善作業の経緯や変更履歴を、実行用スキル本文へ蓄積しない

### 9. 改善を検証する

更新しただけで完了とするな。

最低限、次の評価ケースを作れ。

1. 元セッションの、指摘を受ける前の依頼
2. 同じ設計上の弱点を含む近接事例
3. 似ているが、その規則を適用すべきでない事例

元セッションから抽出した各 `F-*` に対し、改善後の設計出力が次を満たすか判定せよ。

- 問題になった要件、制約、非目標を保持している
- 指摘対象の設計判断を、実装前に扱っている
- 必要な代替案、根拠、トレードオフを示している
- 必要な品質、運用、移行、検証の観点を示している
- 余計な設計または対象外の機能を追加していない
- 実装者が一意に判断するための情報が増えている

可能なら、変更前のスキルによる出力と変更後のスキルによる出力を同じ条件で比較せよ。主観的な印象だけでなく、指摘から作った合否条件を使え。

変更後が改善していない、別の重要な挙動を壊した、または不必要に冗長になった場合は、変更案を見直して再検証せよ。

### 10. 結果を報告する

次の構成で報告せよ。

```markdown
# 設計スキル改善結果

## 対象

- セッション: ...
- 改善対象スキル: ...

## セッションの設計経緯

- 当初の目的と制約
- 当初の設計方針
- 主な指摘
- 最終的な修正方針

## 抽出した指摘

| ID  | 根拠 | 設計上の問題 | 原因 | 受け入れられた修正 | 重要度 |
| --- | ---- | ------------ | ---- | ------------------ | ------ |

## スキル変更判断

| 指摘 ID | 判断 | 変更する規則 | 理由 |
| ------- | ---- | ------------ | ---- |

## 適用した変更

- 変更箇所
- 変更前
- 変更後

## 検証結果

| 評価ケース | 確認内容 | 変更前 | 変更後 | 判定 |
| ---------- | -------- | ------ | ------ | ---- |

## 採用しなかった項目

- 項目
- 採用しなかった理由

## 未解決事項

- 根拠不足またはセッション内で決着していない事項

## 最終状態

- 更新済み | 変更不要 | 検証不合格 | 作業停止
```

## 停止条件

検証の操作が失敗した場合、依存不足の解消や一時的な失敗の再試行など、原因に応じた復旧を試みよ。

次の場合は推測で続行せず、理由を記録して停止せよ。

- 指定セッションを特定または読取できない
- 改善対象の設計用スキルを読取できない
- 更新に必要な操作が失敗した
- 原因に応じた復旧を試みても、検証に必要な操作を完了できない
- 対象セッションが設計依頼ではなく、設計用スキルへ一般化できる証拠がない

停止後に別セッションを探したり、無関係な変更を行ったりしてはならない。
