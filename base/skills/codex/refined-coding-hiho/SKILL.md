# 継続して使う判断基準の文書化

- 実装依頼で今後も使う判断基準が示された場合は、既存の仕様や開発規約が対象範囲と例外まで定めているか確認する。不足する範囲だけを適切な文書へ実装と併せて反映し、実装が既存規約に違反しているだけなら文書へ同じ規則を追加しない。判断基準が個別の修正やPRの説明にしか残らないと、次の実装時に見落としやすいため。
- 機能の目的や理念を文書化する場合は、目的と対象だけを記し、その時の調査で注目した優先度や判定条件を混ぜない。必要な判定方法は仕様の該当箇所へ記す。実現手段を目的へ混ぜると、今回注目した状況だけへ機能の対象を狭めてしまうため。

# 保存設定の削除

- 保存設定の項目を廃止する場合は、同じ設定管理で項目を削除したマイグレーションを調べ、同種の既存例があればその方式で削除を記す。スキーマが未知のキーを自動除去できることだけで省略しない。機能上は不要でも、設定変更の管理方法を周囲と揃えるため。
- 設定項目を削除し、既存の読み込み・マイグレーションテストで削除後の状態を検証できる場合は、そのテストやスナップショットを更新し、共通処理によるキー除去だけを確認する旧値ごとの専用テストを増やさない。周囲の検証粒度を保ち、削除項目ごとの保守負担を増やさないため。値の変換や固有の不具合を検出するテストは別に判断する。

# 作業場所を変えた実装の委任

- 別のworktreeやcheckoutで実装を委任する場合は、親エージェント自身が実際の作業先のAGENTS.mdを読み、テスト追加の可否などの制約を委任内容と最終差分に照合する。元の作業場所や共有コンテキストと規約が一致するとは限らず、子の完了報告や検証成功だけでは規約違反を見落とすため。

# GitHubへ載せる参照リンク

- 実装の経緯をGitHubのPR本文やコメントに書く場合は、Issue・PRへのリンクや参照記法が参照先に記録されることを考慮し、参照先の相手の判断や対応にも役立つものだけを載せる。調査事例を紹介するだけの参照は省き、必要な観測事実は本文で説明する。自分の変更理由を示すのに便利でも、相手には不要な情報が届きうるため。

# ユーザー向けUIの表示

- 複数の表示領域がある画面でUIを追加・再配置する場合は、フィルターなどの操作部品の対象を確かめ、特定の一覧やパネルに属する操作を対象と同じ視覚的なまとまりに置く。見出しや囲みを含む完成後の画面で所属関係を確認する。部品単体で正しく動いていても、画面全体や隣接領域への操作と誤認される配置になりうるため。
- UIの説明文や補助見出しを追加・整理する場合は、想定利用者がその画面で行う操作や判断に必要かを先に吟味する。熟練者に自明な説明や、操作目的と関係のない実装上の副作用だけを説明する文は原則省く。表示面積を操作と判断に必要な情報へ割くため。余白が十分なら短い操作案内を残してよいが、省略時も操作状態の通知とアクセシビリティ上の名前は維持する。
- 一覧で比較に使う順位や評価値を個別の詳細画面にも表示する場合は、その画面での判断に必要かを別に評価する。診断にだけ有用な値や計算根拠は、通常表示を占めない折りたたみへ収める。情報の必要性は画面の用途で変わるため。
- 複雑な判定条件をユーザー向けUIで説明する場合は、ユーザーの判断に必要な条件を残したうえで、内部条件を網羅することよりも対象、契機、結果が誤解なく伝わる最小限の文を優先する。説明量が条件同士の関係を隠すため。
- 独立した候補を箇条書きにする場合は、各項目だけで対象と条件を読み取れる完結した文にする。前後の項目や導入文へ係り受けを持ち越すと、候補同士の従属関係を誤認させるため。
- 条件を分類する見出しは、配下のすべてを正しく包含する語にする。条件が複数の軸にまたがる場合は、実装にない排他的な分類を使わない。
- ユーザーに馴染みのない内部用語や評価語をUIへ出す場合は、判定対象や評価観点を短く定義する。名称だけでは利用者が挙動を判断できないため。

# 実在データに基づく実装

- 実在データの形や状態に依存する機能を実装し、閲覧を許可された実データが利用できる場合は、典型例と反例を複数観測し、仕様候補が双方で成立することを確認してから実装方針を確定する。単一の事例や机上の想定だけでは、多重関係や工程差を見落とすため。
- 外部データの収集、関係の導出、永続化、外部出力をまたぐ変更は、代表例の部分実行だけで完了とせず、利用可能なら本番相当の全体経路を通す。該当する場合は、高次数の項目、同じ外部IDを複数の親が参照する項目、上限付近の件数を含める。少数の実例では、識別子の衝突、容量制限、処理対象集合のずれが現れないため。
- UI確認に使うサンプルデータへ新しい表示項目を追加する場合は、空値だけでなく代表的な非空値も含める。スキーマの通過だけでは表示内容とレイアウトを検証できないため。

# 識別子と正規化

- ID付きの入力を集合化または並び替えて正規化する場合は、同じIDを除く前に、そのIDが表す不変の値が一致するか検証する。順序だけを正規化し、一つのIDに複数持てる役割や注釈だけを明示的に併合する。`Set`や先勝ちで矛盾する重複を消すと、異なる事実が同じfingerprintやcacheへ潰れるため。
- 同じ外部オブジェクトが複数の親や工程で別の出来事として現れ、所有対象、発生時刻、行動のいずれかが異なる場合は、永続識別子へ親や工程のscopeを含める。外部オブジェクトのIDだけを共有すると、別々の進捗が衝突または混同されるため。

# 増分処理で保持する状態

- 増分処理では、取得できた項目、今回その派生値を確定した項目、出力へ保持する項目の集合を分け、派生値を更新するのは今回確定した項目だけにする。今回確定しない項目は前回値の存在を検証して保持し、各Mapのキー集合が出力項目の集合と一致することを確かめる。取得成功を再計算完了と扱うと、旧値も新値もない項目を生むため。
- 未再計算の派生値を診断用に保持する場合は、現行入力で確認済みかを示す項目単位の状態も保存し、通知、表示、外部出力は確認済みの値だけに限定する。空配列やunknownへ置き換えると、結果が0件なのか未確認なのかを区別できず、古い値の誤利用や未送信候補の消失につながるため。

# 外部副作用の中断復旧

- 外部サービスへの複数段階の書き込みを中断後に復旧する場合は、最初の書き込み前に操作内容、実行順、一括適用単位、仮参照、照合用の基準値を永続化し、進行段階、外部反映の確度、判明した外部IDを別々に更新する。実行中のメモリ状態やIDの存在だけでは、再起動後に同じ操作の結果か、安全に再開できる段階かを判定できないため。
- 外部書き込みの復旧では、永続化した段階と観測済みの外部状態から未実行と確定できる操作だけを再実行する。読み戻し以降まで確認済みなら外部書き込みを繰り返さずローカル処理だけを再開し、帰属や結果を確定できない操作は未確定として永続化する。一致するIDや現在値だけを成功の証拠にすると、別の対象を採用したり副作用を重複させたりするため。

# 診断ログの所有権

- 同じ失敗が複数の層や非同期の呼び出し元へ伝播する場合は、診断結果を記録済みだけ、未記録だけ、両方を区別できる型にし、利用者への応答に使う元のエラーとともに伝播させる。各境界は未記録分だけを一度記録する。エラー文字列、causeの形、オブジェクト同一性から記録済みかを推測すると、重複記録か記録漏れを起こすため。
- タイマー、ユーザー操作、IPCなどが同じPromiseへ合流する処理では、モード選択や前処理も共有実行の内側に置いて記録担当を一つに決め、合流した呼び出し元は同じ失敗を別に記録しない。記録担当による通知が失敗した場合は、未記録分だけを一つ上の既存エラーバウンダリへ渡す。共有実行の外に失敗しうる処理があると、待機者ごとに同じ失敗を処理するため。
- 外部入力やAI生成物に由来するエラーを永続化する場合は、共通の伏せ字処理をメッセージ、stack、cause、AggregateErrorの全要素へ適用し、検証や再試行の原因は許可した分類と構造だけを保存する。メッセージだけを置換してもstackや入れ子の原因から本文や認証情報が漏れるため。

# 非同期の停止と後始末

- 複数経路から同じ非同期の停止や後始末を開始できる場合は、最初の開始前にエラーの記録責任を決め、開始したPromiseへ直ちに拒否ハンドラーを付けて結果を保持し、後続経路で一度だけ回収する。中断signalを先に送ったり拒否しうるPromiseをfire-and-forgetしたりすると、意図しない呼び出し元の責任が固定されるか、一時的な未処理拒否になるため。
- 後始末の失敗で結果の重複利用や到達不能状態が生じる資源では、後始末の成功前に破棄済み状態や処理結果を確定せず、失敗時は対象を追跡したまま同じ後始末を再試行できるようにする。先に状態だけ進めると、到達不能な結果や孤立資源が残るため。

# 参照を含むDTO

- 参照先を選別または上限付きで収録するDTOへ参照を追加する場合は、参照元の生成、参照先の必須収録、semantic validationを一つの契約として更新する。参照先だけが出力から欠けると、正しい入力でも生成全体が失敗するため。
- 保存や表示の主対象と、関係の正当性を検証する対象範囲が異なる参照では、主対象と範囲を別の値として生成元からsemantic validationまで渡す。表示用IDから検証範囲を復元すると、正当な関係を拒否したり、無関係な関係を受け入れたりするため。

# AIによる自然言語処理と検証

- 既にAIが自然言語を解釈する機能で、定型句や対象名の完全一致が正当な入力を拒否している場合は、表現の列挙を増やさず、操作ごとの成立条件を明文化してAIへ意味判断を任せる。原文の実在、ID、状態遷移、日付形式、外部の定型プロトコルはコードで検証する。言い換えや指示語への対応と機械的な制約を分離し、構造検証を意味の正しさの保証と混同しないため。
- AIへ送る構造化入力では、意味の整合性を確認するcanonical入力とtransportの容量制限を別の契約にする。型、一意性、参照整合性の違反は例外にし、正しく増えうる集合は切断しない。transportの容量を超えた場合は入力不正ではなく、その判定だけの延期または分割として扱う。cacheを使う場合は、完全なcanonical入力で照合してから容量を判定する。通常データの件数増加で処理全体を止めたり、根拠を黙って捨てたりしないため。
- AI生成物の検証失敗をAIへ返して再生成させる場合は、上限を初回を含む総試行回数で定め、生成と検証だけを再試行する。外部書き込みへ進む前に検証を完了し、書き込み開始後の失敗は永続状態に基づく復旧へ分ける。生成再試行へ戻すと外部副作用を重複させるため。
- AIの意味判断を変える場合は、固定応答による構造検証に加え、本番の生成指示で実AIを動かし、その出力を本番の応答解析・検証まで通す。実行全体の成功だけでなく、対象stageの実呼び出し件数と採用結果を確認し、共有予算、cache、延期によって0回なら実AIを検証済みと報告しない。ツール接続を代替した場合は、その検証範囲を本番の通し確認と区別して報告する。固定応答だけでは、実際の生成結果とアプリが受理する契約の食い違いを検出できないため。
- 実AIの受入条件は、必要な対象・操作・値・根拠と、禁止する変更で定める。仕様が要求しない操作数や特定語への確認質問を固定せず、確認後の訂正を検証する入力は確認分岐の仕様に合わせ、必要なら確認手順を明示する。仕様上許された関連操作や直接の提案まで誤って不合格にしないため。

# 検証済み参照の再利用

- 検証済み参照を別の提案へ引き継ぐ場合は、参照IDだけでなく、元の検証が成立した引用・対象・操作・親などの条件も照合する。同じ参照を複数の操作が共有できる契約なら、その共有を許し、IDだけで一意とみなさない。参照の存在だけでは不正な流用を防げず、一対一と決めつけると正当な一対多の提案まで拒否するため。
