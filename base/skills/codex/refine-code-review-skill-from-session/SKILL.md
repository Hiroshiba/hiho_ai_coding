# 目的

指定されたコードレビューセッションを分析し、そのセッションから確認できた再利用可能なレビュー観点を、既存のコードレビュースキルへ反映する。

セッション内の発言をそのまま保存しない。
個別のコード、シンボル名、ファイル名、今回だけの修正手順ではなく、今後のコードレビューと GitHub への投稿で再利用できる条件付きの規則へ変換する。

# 必須入力

次の二つを特定する。

- 対象となる Codex セッション ID
- 改善対象となる既存のコードレビュースキル

どちらかを一意に特定できない場合は推測せず、不足している項目だけを確認する。

# 使用する既存機能

- セッションログの取得には `Hiroshiba/hiho_scripts` の `get_codex_session_jsonl_paths.py` を使用する。詳細は `hiho_get_codex_session_jsonl_paths -h` を実行する。
- コードレビュースキルの更新と評価には Codex 公式の `$skill-creator` を使用する。

これらと同等のログ探索処理、スキル編集処理、評価フレームワークを新たに実装しない。

# 対象範囲

- 指定されたセッションと、ログ取得スクリプトが返した関連ログだけを分析する。
- 他のセッションを無断で追加分析しない。
- 対象セッションのうち、コードレビューとその後の応答に関係する部分を分析する。
- レビュー結果を GitHub へ投稿する段階のやりとりも分析する。PR タイトル、PR 説明、PR コメントの推敲を含む。
- 実装作業、雑談、調査だけの発言をレビュー規則として取り込まない。
- 対象となるプロダクションコードは変更しない。変更対象は指定されたコードレビュースキルと、その評価用リソースだけとする。

# 分析手順

## 1. 現状を確認する

対象セッションのログを取得して読む。

あわせて、改善対象となるコードレビュースキルについて次を読む。

- `~/Github/hiho_ai_coding/base/skills/codex/refined-review-hiho/SKILL.md`
- スキルから参照される関連ファイル
- 既存の評価ケース
- 既存のレビュー規則
- スキルの適用範囲とトリガー条件

分析が終わるまで対象スキルを変更しない。

## 2. レビュー事例を再構成する

ログを単発の発言としてではなく、一連のレビュー事例として読む。

各事例について可能な範囲で次を特定する。

- レビュー対象となった変更と、その目的
- 変更前のコードまたは設計
- Codex が行った指摘または提案
- ユーザーによる訂正、追加条件、反論、承認
- 指摘後に行われたコードまたは設計の変更
- テスト、再確認、後続レビューの結果
- 最終的に指摘が採用、修正、撤回、または未解決のどれになったか

Codex が一度述べただけの内容を、正しい規則として扱わない。
レビューの最終的な採否と、その理由まで確認する。

投稿文の事例では次を特定する。

- Codex が最初に書いた PR タイトル、PR 説明、PR コメント
- ユーザーによる書き直し、追加指示、却下
- 最終的に GitHub へ投稿された文面
- 書き直しで変わったもの。構成、粒度、語調、加えた情報、削った情報

ユーザーが手を入れた箇所だけを根拠とする。
Codex の初稿がそのまま通った部分を、正しい書き方の規則として扱わない。

## 3. レビュー観点を分類する

見落としを防ぐため、各レビュー事例が次のどの観点に関係するかを確認する。

- 設計、責務、抽象化
- 正しさ、仕様との一致
- 境界条件、エラー経路、並行処理
- 複雑さ、過剰設計、保守性
- テストの必要性とテスト自体の妥当性
- セキュリティ
- パフォーマンスとリソース管理
- 命名
- コメントとドキュメント
- コーディングスタイルと既存コードとの一貫性
- レビューコメントの具体性、理由、重大度
- GitHub へ投稿する文章の書き方。PR タイトル、PR 説明、PR コメント

これらは分類と見落とし防止のためだけに使う。
セッションに根拠のない一般的なベストプラクティスを、新しい規則として追加しない。

## 4. 学習候補を抽出する

キーワード一致ではなく、発言、コード変更、ユーザーの反応、最終結果の意味を考えて候補を抽出する。

候補ごとに次を整理する。

- 学びの要約
- 種別
  - コーディング規則
  - レビュー時の検出規則
  - レビューコメントの書き方
  - GitHub へ投稿する文章の書き方
  - 指摘の重大度または優先順位
- 適用される状況
- 適用範囲
  - 全プロジェクト
  - 特定リポジトリ
  - 特定言語またはフレームワーク
  - 特定ディレクトリまたはコンポーネント
- レビュー時に確認すること
- 指摘する条件
- 問題となる理由または具体的なリスク
- 指摘しない条件または例外
- 重大度
- 根拠となるレビュー事例
- 確信度
- 既存スキル内の関連規則

## 5. 学習候補を選別する

次を満たす候補だけを、対象スキルへ反映する候補とする。

- 今回の特定の行やシンボルだけに依存せず、再利用できる
- 何を確認し、どの条件で指摘または記述するかが具体的である
- ユーザーの明示的な訂正、採用された修正、再確認結果、または一貫した複数の根拠がある
- 既存スキルと重複していない
- 既存の規則やプロジェクトの方針と矛盾していない
- 適用範囲を必要以上に広げていない
- レビュー時または投稿文の作成時に実際に判定可能である
- コードベースの健全性、レビュー品質、または投稿文の伝わりやすさを改善する

次の候補は反映しない。

- Codex の未確認の推測だけを根拠とするもの
- 最終的な採否が確認できないもの
- ユーザーの反論が妥当だったため撤回された指摘
- 一度限りの作業手順
- 一般化すると誤検出が増えるもの
- 単なる好みであり、ユーザーまたはプロジェクトの方針として確認できないもの
- 「丁寧にレビューする」「問題を見逃さない」など、具体的な行動へ変換できないもの
- ユーザーが書き直さなかった箇所から作った、投稿文の書き方

作者からの反論があった場合は、元の指摘を維持する前に反論の妥当性を検討する。
反論が正しければ、元の指摘を正の規則として取り込まない。

スタイル上の指摘は、プロジェクトの既存ルール、一貫性、またはユーザーの明示的な方針に基づく場合だけ採用する。
必須ではない改善は、ブロッキングな規則ではなく任意の指摘として扱う。

## 6. レビュー規則へ変換する

一つの規則には、原則として一つの適用条件と一つのレビュー行動を持たせる。

対象スキルへ追加または更新する規則は、必要に応じて次の内容を含める。

### 規則名

- 適用条件: どのような変更、コード、言語、ディレクトリに適用するか
- 確認事項: レビュー時に何を調べるか
- 指摘条件: 何が確認された場合に指摘するか
- 理由: どのような不具合、保守性低下、利用者影響につながるか
- 重大度: 必須、任意、Nit など
- 例外: どの条件では指摘しないか
- 例: 根拠となるセッションから一般化できる場合だけ、悪い例と望ましい例を示す

投稿文の規則には次を含める。

- 適用条件: PR タイトル、PR 説明、PR コメントのどれに適用するか
- 書くこと
- 書かないこと
- 例: 根拠となるセッションから一般化できる場合だけ、望ましい文面と避ける文面を示す

規則は短い命令形で書く。
抽象的な理念だけで終わらせず、レビュー時に実行できる確認行動を書く。

セッションの文章をそのまま貼り付けない。
特定コミットの行番号や固有名詞を、規則の理解に不要であれば残さない。

新しい規則を末尾へ追加し続けるのではなく、既存規則と意味が重なる場合は統合または書き換える。
古い規則が新しい学びと矛盾する場合は、両方を残さず、根拠を確認して一つの規則へ整理する。

リポジトリ、言語、フレームワーク固有の規則を、全プロジェクト向けの規則にしない。
対象スキルが参照ファイルを使っている場合は、既存の構成に合わせて適切な範囲へ配置する。

## 7. `$skill-creator` に改善を委ねる

抽出した候補、採用理由、除外理由、適用範囲、既存スキルとの対応関係を `$skill-creator` に渡す。

既存のコードレビュースキルを改善対象として指定し、別名の代替スキルを新規作成しない。

スキルの編集、旧版との比較、評価、再調整は `$skill-creator` の既存スキル改善フローに委ねる。
独自のスキル改善フローを並行して実装しない。

評価では、少なくとも次の意図を `$skill-creator` に伝える。

- 学習元の問題と同種の問題を、新しいスキルが指摘できること
- 見た目は似ているが問題ではないケースを指摘しないこと
- 規則の適用範囲外では発動しないこと
- 重大度を必要以上に高くしないこと
- 指摘時に具体的な問題と理由を説明できること
- 投稿文の規則が、ユーザーが書き直した文面の方向を再現できること
- 投稿文の規則が、レビュー指摘そのものの書き方へ波及しないこと
- 既存スキルで正しくできていたレビューを悪化させないこと
- 通常のコードレビュー依頼では対象のレビュースキルが適切に使われ、この改善用スキル自体は誤って使われないこと

変更後のスキルが旧版より改善していると確認できない場合は、その候補を反映しないか、規則を狭めて再評価する。

## 8. 結果を報告する

最後に次を簡潔に報告する。

- 分析したセッション ID
- 改善したコードレビュースキル
- 追加した規則
- 修正した規則
- 削除または置き換えた規則
- 反映しなかった候補と理由
- 各変更の根拠となったレビュー事例
- `$skill-creator` による旧版と新版の評価結果
- 変更したファイル
- 未解決または確信度が不足している点

# 変更しない条件

次の場合は対象スキルを変更せず、その理由を報告する。

- 再利用可能で十分な根拠を持つ学びがない
- 抽出した学びがすべて既存スキルへ既に含まれている
- レビューの最終結果が確認できない
- セッションがコードレビューのセッションではない
- 対象スキルを特定または読み込みできない
- 新しい規則が評価で改善を示さない
