# 目的

指定されたCodexの実装依頼セッションを分析し、そこで示されたコーディング上の指摘を、将来の実装でも役立つコーディング規則へ変換する。

単に指摘を列挙したり、ログ中の発言をそのままコーディング用スキルへ追記したりしない。

既存のコーディング用スキルを、実際の利用結果に基づいて、最小限かつ一貫した形で改善する。

# 入力

次の2つを対象として作業する。

- 対象となるCodexセッション
- `~/Github/hiho_ai_coding/base/skills/codex/refined-coding-hiho/SKILL.md`

# 既存機能の利用

- セッションログの取得には `Hiroshiba/hiho_scripts` の `get_codex_session_jsonl_paths.py` を使用する。詳細は `hiho_get_codex_session_jsonl_paths -h` を実行する。
- 既存のコーディング用スキルの更新と評価には、Codex公式の`$skill-creator`を使う。独自のスキル作成・改善機構を実装しない。

# 基本原則

- ログを調べる観点は広く持ち、コーディング用スキルへ追加する規則は厳しく絞り込む。
- Codexがすでに通常行える一般的な助言ではなく、今後の判断を実際に変える非自明な情報を残す。
- 一つのタスク固有の事情、一時的な例外、一度の失敗を、無条件の普遍的な規則へ変換しない。
- 指摘の表現ではなく、その背後にある問題、望ましい振る舞い、理由、適用条件を抽出する。
- 新しい規則を追加する前に、既存のコーディング用スキルに同じ内容や矛盾する内容がないか確認する。
- 変更が不要という結論も正しい結果として扱う。

# 作業手順

## 1. セッション全体を理解する

対象セッションが実装依頼のセッションであることを確認する。

取得したログを会話の時系列に沿って読み、少なくとも次を把握する。

- 元の実装依頼
- ユーザーが明示した要件と制約
- Codexが選んだ設計や実装方針
- 作成または変更した実装
- 作成または変更したテスト
- 作成または変更したコメント
- 作成または変更したドキュメント
- ユーザーやレビュー担当者からの指摘
- 指摘後に行われた修正
- 指摘が後から撤回、変更、限定されたか
- 最終的に採用された状態
- 未解決のまま終わった論点

一つの発言だけを切り出して解釈しない。指摘の前後、対象となった実装、修正後の応答まで読む。

Codex自身による説明、推測、自己評価は、ユーザーやレビュー担当者による指摘と区別する。

## 2. コーディング上の指摘候補を抽出する

実装、テスト、コメント、ドキュメント、およびそれらを作るための実装判断に関する指摘を抽出する。

指摘を見落とさないため、次の観点からセッションを確認する。

### 要件とスコープ

- 元の依頼や受け入れ条件を満たしていたか
- 明示された制約を無視していなかったか
- 依頼されていない変更を広げていなかったか
- 利用者から見た挙動が意図どおりだったか

### 設計と統合

- 変更全体の設計が妥当だったか
- 既存のアーキテクチャや抽象化と整合していたか
- 既存機能を再利用すべきところで重複実装していなかったか
- 責務や依存関係の置き場所が適切だったか
- 変更箇所だけでなく、周辺コードやシステム全体との整合が取れていたか

### 正しさ

- 通常ケースで正しく動作するか
- エッジケース、異常系、境界値を扱えているか
- 並行処理、競合、順序依存の問題がないか
- 状態の不整合やデータ破損を起こさないか
- 外部から見える契約や既存の挙動を壊していないか

### 複雑さと保守性

- 必要以上に複雑な実装になっていないか
- 一つの関数やクラスへ責務を詰め込みすぎていないか
- 不要な抽象化や、依頼されていない機能を追加していないか
- コードを自然な順序で読んで理解できるか
- 重複や将来不整合になりうる実装がないか

### 命名とスタイル

- 名前が役割や意味を正確に表しているか
- プロジェクトで合意されている規約と整合しているか
- 言語やフレームワーク固有の規則を、別の対象へ誤適用していないか
- 自動化されたフォーマッターやリンターの責務と重複していないか

### エラー処理と非機能要件

- エラーが必要な場所で明示的かつ適切に扱われているか
- エラーを握りつぶしたり、誤解を招く形へ変換したりしていないか
- セキュリティ上の問題がないか
- 機密情報や個人情報を不適切に保存、表示、記録していないか
- 不要な計算、I/O、データベースアクセス、メモリ使用がないか
- リソースの解放や後始末が正しいか

### テストと検証

- 変更された挙動に対応するテストがあるか
- テストが実装の内部構造だけでなく、必要な振る舞いを確認しているか
- 通常ケースだけでなく、エッジケースや異常系を扱っているか
- テスト自体の前提や期待値が正しいか
- 必要なビルド、型検査、リンター、テスト、実動作確認を行ったか

### コメント

- コメントがコードから分かる「何をしているか」を重複していないか
- コメントが判断理由、制約、非自明な背景を説明しているか
- 実装変更後もコメントが正しいか
- コメントで補うよりコードを単純化したほうがよくないか

### ドキュメント

- ユーザー向けの変更がドキュメントへ反映されているか
- README、API説明、設定例、使用例が実装と一致しているか
- 古い説明や誤解を招く表現を残していないか
- 読者に必要な前提、制約、失敗時の挙動が説明されているか

各指摘候補について、次を整理する。

- 何が問題だと指摘されたか
- どの実装、テスト、コメント、ドキュメントが対象か
- どう直すことを求められたか
- なぜそれが必要なのか
- 修正後にどうなったか
- 最終的にその方針が維持されたか

このチェックリスト自体を、そのままコーディング用スキルへ追加してはならない。
ログ中に根拠のある項目だけを規則候補にする。

## 3. 再利用可能な学びか判定する

各指摘候補について、次を判断する。

- 将来の別の実装でも起こりうる問題か
- ユーザーが今後も適用したい方針か
- Codexの判断を実際に変える非自明な情報か
- 指摘の理由を説明できるか
- 適用条件を説明できるか
- 適用範囲を限定できるか
- 指摘後の修正が採用または支持されたか
- 既存のコーディング用スキル、プロジェクト規約、リンター、テストなどですでに十分に扱われていないか

適用範囲を次のいずれかとして判断する。

- すべてのコーディングに適用する一般規則
- 特定のプロジェクトまたはリポジトリに適用する規則
- 特定のディレクトリ、ファイル種別、言語、フレームワークに適用する規則
- 今回のタスクだけに適用する一回限りの条件

一回限りの条件はコーディング用スキルへ追加しない。

一度だけ現れた指摘であっても、ユーザーが一般的な方針として明示しており、適用条件と理由が明確なら規則候補にできる。

次のものは追加しない。

- その実装だけに必要だった特殊対応
- 一時的な移行措置
- 後から撤回された指摘
- 結論が出ていない議論
- Codex自身の推測だけに基づく改善案
- 理由や適用条件を説明できない規則
- 「正しいコードを書く」などの一般論
- 既存規則の単なる言い換え
- 自動ツールが完全に強制している細かなスタイル規則
- プロジェクト固有の事情を無条件に一般化した規則

## 4. コーディング規則へ書き換える

採用する指摘を、短く、具体的で、自立した命令形の規則へ書き換える。

一つの規則では一つの論点だけを扱う。

可能な限り、次を含める。

- 適用される条件
- 行うこと、または避けること
- その理由
- 適用範囲
- 必須要件なのか、望ましい選択なのか

基本形は次とする。

> `[適用条件]の場合は、[行うこと／避けること]。[理由]のため。`

適用範囲が自明でない場合は明示する。

必要な場合だけ、短い「避ける例」と「推奨例」を加える。
例が規則の理解を変えないなら加えない。

ログ中の固有の変数名、ファイル名、Issue番号、セッション固有の事情は、規則の理解に不可欠でない限り取り除く。

プロジェクト内に正本となる設計文書、実装例、設定ファイルがある場合は、その内容を大量に複製せず、どの状況でそれを参照するかを書く。

## 5. 既存のコーディング用スキルへ統合する

Codex公式の`$skill-creator`を使って更新する。

更新前に、対象スキルの本文と関連する参照ファイルを読む。

新しい規則ごとに次を行う。

- 同じ意味の既存規則がある場合は、新しい規則を追加せず、必要な部分だけ明確化する。
- 既存規則の適用範囲が広すぎる場合は、条件やスコープを追加する。
- 新しい証拠が既存規則を明確に置き換える場合は、古い規則を更新または削除する。
- 既存規則との矛盾が解決できない場合は、推測で両方を残さず、更新を保留して報告する。
- 無関係な既存指示、メタデータ、呼び出し方針は変更しない。

共有される目的、重要な制約、頻繁に使う規則は`SKILL.md`へ置く。

特定の言語、フレームワーク、ファイル種別だけに必要な詳細や、長い例は、必要な場合だけ参照ファイルへ分離する。

スキルを長くすること自体を改善と見なさない。
追加よりも、既存規則の明確化、統合、適用範囲の修正を優先する。

## 6. 更新結果を検証する

`$skill-creator`を使い、スキルの構造と実際の振る舞いを評価する。

少なくとも次を確認する。

- 元の指摘と似た状況で、新しい規則が問題を防ぐか
- 少し条件が異なる状況でも、理由に基づいて適切に判断できるか
- 関係のない実装を不必要に拘束しないか
- 特定のプロジェクトや言語だけの規則が、別の対象へ適用されないか
- 同じ内容や矛盾する内容が重複していないか
- スキルのdescriptionが、対象となる依頼と対象外の依頼を区別できるか

可能な場合は、新しいコンテキストで現実的な依頼を使い、スキルありとスキルなしの結果を比較する。

生成された文章の表現が一致するかではなく、実装上の判断や成果物が改善されたかを確認する。

評価で過剰適用や回帰が見つかった場合は、規則を増やす前に、適用条件とスコープを狭める。

## 7. 結果を報告する

最終報告には次を含める。

### セッションから確認した指摘

各指摘について、対象、問題、求められた修正、理由、最終的な結果を簡潔に示す。

### コーディング用スキルへ反映した内容

各変更について次を示す。

- 反映した規則
- 対応する指摘
- 適用範囲
- 新規追加、既存規則の修正、統合、削除のいずれか
- その形に一般化した理由

### 反映しなかった内容

一回限り、未解決、重複、すでに自動化済み、根拠不足など、反映しなかった理由を示す。

### 変更したファイル

変更したスキルファイルとセクションを示す。

### 検証結果

実行した評価と、期待した判断が得られたかを示す。

再利用可能な規則が見つからなかった場合は、無理にスキルを変更せず、その結論と理由を報告する。

# 完了条件

次のすべてを満たしたときに完了とする。

- セッション全体と最終的な結論を確認した
- コーディング上の指摘を対象成果物と結び付けた
- 一回限りの条件と再利用可能な規則を区別した
- 各規則に適用条件、望ましい行動、理由、適用範囲がある
- 既存規則との重複や矛盾を確認した
- `$skill-creator`を使って最小限の更新を行った
- 元の問題を防ぎつつ、無関係な実装を拘束しないことを評価した
- 反映した内容と反映しなかった内容を報告した
