# subagentを使った開発マネジメント

あなたはユーザーからの開発タスクを受け取って完遂するメインエージェントのあなたです。
調査・実装・検証は、作業量にかかわらずsubagentに任せます。
あなたは報告を受けて、次の行動を判断します。

調査・実装・検証を始める前に、対象リポジトリを作業ディレクトリにして、[scripts/sync-default-branch.sh](scripts/sync-default-branch.sh) を subagent に `bash` で実行させてください。
スクリプトのパスは、この `SKILL.md` があるディレクトリを基準に解決してください。
スクリプトは `upstream` があれば使い、なければ `origin` を使って、リモートのデフォルトブランチを取得します。
現在のブランチがデフォルトブランチで、リモートより遅れている場合だけ `git merge --ff-only` で追従します。
別ブランチでは、現在のブランチ名と、現在の HEAD がリモートのデフォルトブランチより遅れているかをログに出します。
スクリプトが失敗した場合は先に原因を解消し、再実行が成功してから依頼された作業に進んでください。

調査や実装のタスクを切り分けてください。
タスクの分割粒度は任せます。
分割タスクごとにコミットしてください。

実装する場合は、ログへ出た「ワークツリーの基点」からGitのワークツリーを作ってください。

次にsubagentに指示していってください。

- メインエージェントのあなたは使用するトークン数をなるべく節約し、作業はsubagentに任せてください
- コードの把握や既存実装との比較、Gitの履歴やログの調査は、subagentに任せてください。短いコマンドや読み取り専用の操作も対象です
- subagentは、設計はモデルSolのeffort maxを、ドキュメント変更はモデルAstraのeffort xhighを、実装・調査・実行・その他はモデルlunaのeffort maxを起動してください
- テストや検証用スクリプトの作成・実行、CI監視もsubagentに任せてください
- メインエージェントのあなたは絶対にコードを変更してはいけません
- メインエージェントのあなたは絶対にPlaywrightを実行してはいけません
- メインエージェントのあなたは絶対にスクリーンショットを見てはいけません
- subagentには、単独で完了を判断できる1つの成果を委任してください
- 依頼には、期待する成果、担当範囲、確定済みの判断、完了条件を含めてください。既存コードや共有済みの規約から判断できる進め方はsubagentに任せてください
- 同じsubagentを続けて使うのは、同じ成果を完成させる作業である場合です。同じ差分への指摘修正は同じ成果として扱ってください
- 期待する成果、担当範囲、レビュー観点のいずれかが変わった場合は、新しいsubagentへ必要な判断だけを引き継いでください
- 新しいsubagentには `fork_turns: "none"` を使い、依頼を自己完結させてください。画像など依頼文へ移せない入力が必要な場合だけ、その入力を含む最小のターン数を `fork_turns` に指定してください。`fork_turns: "all"` は使わないでください
- ユーザーから追加の指示を受けた場合や別のスキルを使う場合も、同じ成果を完成させる作業かを判断してから、担当するsubagentを決めてください。調査・実装・検証は引き続きsubagentに任せてください
- 独立して結果を統合できる作業は並列に委任できます。変更範囲や判断が重なる作業は1つのsubagentへまとめてください
- コードレビューの判断はメインエージェントのあなたが行ってください。直接読むコードは、subagentが示した差分・根拠とその周辺に限ってください。新しいコマンドで根拠を集める必要が出たら、それは調査としてsubagentへ依頼してください
- subagentには、結論と根拠、検証結果、未確認事項を簡潔に報告するよう伝えてください。根拠には、ファイル名と行番号、コミットID、実行結果のURLなどを添えてもらってください
- 報告の根拠が足りない場合は、subagentに追加の調査や報告を求めてください。自分で同じ調査や検証をやり直してはいけません
- git worktree add・git commitはメインエージェントのあなたが行ってください。その際、対象ブランチや変更ファイル、ステージした内容、空白エラーを確認して構いません
- Playwrightを使った動作確認もsubagentに行わせてください。失敗時にどうするかも伝えないと変な行動をしだすので気をつけてください
- UIの変更がある場合は、subagentに実際にスクショ画像を見ながら調整するように伝えてください
- ユーザーが読む手順書は、subagentが書いた文章をメインエージェントのあなたが調整してください
- subagentの作業中は、`wait_agent`で完了通知を待ってください。`sleep`と`list_agents`を組み合わせた定期確認や、進捗確認だけを目的としたメッセージを繰り返さないでください
- 追加の判断や新しい情報がある場合、またはsubagentが進行不能になった場合だけ、作業中のsubagentへ連絡してください
- subagentからの途中経過をそのままユーザーへ中継せず、判断が必要なことやユーザーに影響する節目だけを要約して伝えてください

以下はトークン数をなるべく減らすコツを、別セッションのエージェントに聞いたときのメモです。参考にしてください。

- 重い確認作業が必要な場合は、全タスク完了後に1回だけ行うようsubagentに指示してください
- subagentはスクリーンショットをリポジトリ直下へ残すことがあります。コミット前に消してください
- 大きい調査は観点ごとに分割して並列に投げてください。1つに詰め込むと完走しません
- subagentへ依頼するとき、調査の結果で直さないと判断したものは根拠と一緒に必ず報告するように伝えてください

Githubなどの外部サービスの状態を変える操作、外の何かを更新してしまうコードは指示がない限り実行しないでください。
このPC内であっても、本ディレクトリ・git worktree ディレクトリ以外への変更はやむを得ない場合を除き行わないでください。
pnpmやuvなど、必須だけど実行するだけで他ディレクトリへどうしても影響があるものはやむを得ないので大丈夫です。

タスクが全て完了するか、私に聞く必要が絶対あるものを聞いて待機するまで続けてください。

なるべく任せたいので、確認が必須じゃなければaskなしでお願いします。

## プルリクエストを作成する場合

PR作成の指示があった場合は、タスクがすべて終わったあとに`contribute-voicevox-github`スキルを実行して、適切な粒度でプルリクエストを作ってください。
独立したPRならそのままデフォルトブランチへのPRに、直列するPRならベータ機能のGithub Stacked PRを使ってPRを作ってください。

PR作成後、ユーザーにURLを伝えてください。
その後、CI通過とコンフリクト発生の監視をsubagentへ依頼してください。
subagentには、`gh run watch`や`gh pr checks --watch`などで監視し、完了したときや対応が必要な問題が見つかったときに報告するよう伝えてください。
修正が可能ならもう一度`manage-development-with-codex`スキルを使って修正してください。
完了を待っている間の報告は一切不要です。

この状態まで進んだらユーザーのマージ報告を待ってください。
PRがマージされたら次に進んでください。

ローカルブランチとワークツリーを削除してください。

### 正しく動作しなかった場合

もう一度`manage-development-with-codex`スキルを使ってやり直してください。
正しく動作するまでやり直してください。

## 上記のすべてが完了した場合

最後に、あなたが実際に失敗した・手間取ったため、今後あなたにタスクを依頼するときにあなたへ伝えると使用するトークン数がより減りそうなプロンプトがあれば提案してください。
