# subagentを使った開発マネジメント

メインエージェントは、依頼の完了条件、段階とタスクの分割、担当の選定、報告の統合、レビューの採否、ユーザーへの報告を担います。
コードや文書の調査・変更・検証、Git操作、外部サービス操作は、短い読み取りも含めてsubagentへ任せてください。
メインエージェントはPlaywrightを実行せず、スクリーンショットも見ません。
直接行う操作は、subagentの起動・連絡・待機・終了、報告の統合、ユーザーへの連絡に限ります。
別スキルの読み込みなどメインにしかできない制御操作と、以下の進捗ファイルの読み書きは例外です。

進捗はworktree直下の `hiho_development_progress.yaml` に記録し、メインエージェントだけが更新してください。
承認前やworktree作成前、worktreeを使わない調査では作業ディレクトリ直下に置きます。
worktree作成後はそこへ正本を移し、二つのファイルを並行して更新してはいけません。
各委任・次の判断の直前に、その時点の正本を実際に読み直してください。
会話の記憶や直前の更新差分を、正本の読み直しの代わりにしてはいけません。
報告を受けた後や判断を決めた後には、読み直しとは別に更新してください。
会話全文、経過時間、変化のない途中経過は記さず、次の判断に必要な成果と根拠を残します。ユーザー向けの途中報告を減らす指示は、進捗の記録を省く指示と混同しないでください。

- 段階とタスクの成果、範囲、受入条件、依存関係、状態
- 適用するスキルと適用範囲、ユーザーの指定
- 担当ID、モデル、必要な判断に照らした選定理由
- 根拠の所在、検証結果、未確認事項、差し戻しと検証失敗の経緯
- レビュー指摘の採否と理由、残作業、次の操作、次段階への移行条件

このファイルはコミットに含めないでください。

## 設計・実装のスキルを適用する

設計担当には、設計着手の直前に `refined-codedesign-hiho` を読み、対象に関係する規則を適用させてください。
実装担当には、実装着手の直前に `refined-coding-hiho` を読み、対象に関係する規則を適用させてください。
再設計やレビュー指摘の修正にも同じ規則を適用し、一人の担当が設計と実装を行う場合は、それぞれの着手前に対応するスキルを読ませます。

ユーザーが `refined-fine-grained-coding-hiho` の使用を指示した場合は、指定された範囲の実装着手前に `refined-coding-hiho` と併せて読ませ、適用させてください。
「ファイングレインドで」「細やかな実装で」など、適用意図が明確な言い換えも同じ指定として扱い、OSSであることだけを理由に有効化しません。
指定と適用範囲は担当交代、指摘修正、レビューにも引き継ぎ、途中の指定や変更は進捗を更新して作業中の担当にも伝えてください。

メインエージェント自身は、委任内容やレビュー指摘の採否の判断に必要なときに、これらのスキルの該当箇所を読んでください。
初回の一括読み込みや委任ごとの再読は必須にしません。

## 計画と担当を決める

大きな依頼はまず段階へ分け、各段階を単独で完了判定できる実行タスクへ分けてください。
段階は独立してレビュー・検証できるPRのまとまりとし、固定の行数では区切りません。
複数の小変更をまとめても受入条件と不変条件を確認でき、まとめて検証・レビューできるなら、同じ段階とPRに入れてください。
助言の項目数やファイル数だけでPRを増やさず、まとめると中間状態や検証が曖昧になる変更は分けます。
Solに必要な調査、方針、段階とタスクの分割をまとめさせ、メインエージェントが範囲、中間状態の整合性、粒度、受入条件を判断してください。
1タスクで完了する依頼は、無理に分割しません。

実装前に、保持する既存挙動、変更可能な範囲、設計上の選択、受入条件を確定させてください。
検証計画を決める際は、対象版の要件・設計文書と既存の検証手順を確認してください。自動テストの追加に制限がある場合は、その制限を受入条件へ含めてください。
テストを整理する段階では、既存ケースと検証が守る契約を対応付け、公開経路で残す保証と削る重複・内部手順を受入条件へ含めてください。
変更の入口から最終利用先までの影響経路と不変条件も含め、状態をまたぐ変更では生成・変換・保存・再読込・利用・最終検証の境界を確認させます。
リリース作成や配布運用の変更を含む場合は、タグやReleaseの作成前に、版コミットと既定ブランチの関係、pushで動く公開処理、PRのマージ方式、既存配布先の利用、公開前後の検証を担当に照合させてください。現在の手順に沿うだけで後続のブランチ反映が成立するかまで確認し、成立しない場合は外部操作前に段階と受入条件を組み直します。
初回提案には第1段階でできることとできないこと、残る段階と作業、依存関係、次段階への移行条件、外部操作とユーザーの操作を待つ地点を含めてください。
PRを作る計画には、この依頼で作るworktreeとローカルブランチのマージ後の削除を対象名付きで示し、squash mergeで通常削除が拒否された場合に強制削除する条件も明記してください。
ユーザーには1タスク3行程度で成果、範囲、受入条件を示し、実装着手前にOKを待ってください。
簡単な調査や、すでに続行を許可された範囲では不要な再確認をしません。
承認済みの範囲は自律的に進め、段階が進むたびに一律の再承認を求めないでください。
範囲や受入条件が実質的に変わる場合は計画へ戻ります。
ユーザーが途中で作業ツリーを変更して採用方針を示した場合も、以前の計画を固定せず、現在の差分と新しい受入条件を照合してください。
ユーザーが予定した検証の省略を明示して続行を求めた場合は、未確認の範囲と代わりに確認できる範囲を進捗へ記録し、該当する公開文面やPR本文に反映させてください。通常の公開手順の完了条件は、今回だけの例外で書き換えないでください。

モデルは作業名ではなく、成果を出すために必要な判断で選んでください。

| モデルとeffort                | 選ぶ条件                                                                                                   |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Luna `gpt-6-luna` / `max`   | 方針と受入条件が確定しており、それに沿った根拠収集や実行を進める                                           |
| Sol `gpt-6-sol` / `max`     | 方針が未確定、複数制約の調整が必要、設計や判断が難しい                                                     |
| Astra `gpt-6-astra` / `xhigh` | セッション外の第三者が読む日本語ドキュメントやPR本文の執筆・推敲を主な成果とし、ファイルに仕上げる場合だけ |

扱う資料の種類ではなく、担当自身が作る成果で選んでください。
文書に関係する調査や読み取り専用の判定も、必要な判断に応じてLunaかSolを選んでください。
実装やレビューという名称だけでLunaへ固定せず、複雑な実装や反証の判定にも必要に応じてSolを選んでください。
Astraには他担当が集めた目的、変更事実、根拠ファイルと行番号、検証結果、残余リスクを渡します。
全文のコード調査をやり直させず、執筆に必要な根拠の確認は認めてください。
通常のチャット、内部の進捗YAML、機械用設定の編集はAstraへ回しません。
PRの調査と執筆を分離すると重要な判断が欠ける場合は、Solが一体で行ってもかまいません。
Astraが作った本文ファイルを使うPR操作やCI監視は、必要な判断に合う別の担当へ任せます。

新しい依頼には、同じモデルを使う場合も毎回新しいagent IDを使ってください。
同じ担当への再依頼は、原因が解消した後に、長いタスクの最後で失敗したコミットだけを再実行するような、短く限定された同一操作に限ります。
新しい実装、指摘修正、再設計、再レビュー、追加調査、別タスクはこの例外に含めません。
一人の担当が1回の依頼内で調査・実装・局所検証まで完結することと、進行中の担当へ新しい情報や判断を伝えることは認めます。
工程名だけで担当を細かく分ける必要はありません。

新しいsubagentには `fork_turns: "none"` を使い、期待する成果、担当ファイルと範囲、確定判断、検証・テストの方針、受入条件、根拠の所在を自己完結した依頼として渡してください。
設計・実装・レビューの依頼には毎回、適用するスキルの正確な名前と適用範囲、着手前に読んで適用する指示を含めてください。
依頼全体の履歴を毎回全文渡さず、既存コードや規約から判断できる進め方は担当へ任せます。
画像など依頼文へ移せない入力が必要な場合だけ、その入力を含む最小のターン数を指定し、`fork_turns: "all"` は使いません。
報告には結論と根拠、検証結果、未確認事項、直さなかった事項と理由を求め、ファイル名と行番号、コミットID、実行結果のURLなどを添えさせてください。

## 順次実行と検証

タスクは一つずつ順次実行し、調査を含めて並列に委任しないでください。
各タスクでは担当自身が局所検証を行い、独立レビューはタスクごとに入れず段階末にまとめます。
各段階の実装、必要な検証、独立レビュー、採用した指摘への対応を終えてから次へ進んでください。
PR作成を依頼されている場合は、その段階のPR作成と通常のCI確認も終えます。
次段階の実行や検証にマージ済みの状態が必要なら待ち、コード依存があってもstacked PRで実行・検証できるならマージを待つ必要はありません。

Git操作を含む開発が許可されている場合は、調査・実装・検証に先立ち、最初の担当に対象リポジトリを作業ディレクトリとして [scripts/sync-default-branch.sh](scripts/sync-default-branch.sh) を `bash` で実行させてください。
スクリプトのパスは、この `SKILL.md` があるディレクトリを基準に解決します。
スクリプトは `upstream` があれば使い、なければ `origin` を使ってリモートのデフォルトブランチを取得します。
現在のブランチがデフォルトブランチでリモートより遅れている場合だけ `git merge --ff-only` で追従します。
別ブランチでは、現在のブランチ名と、現在のHEADがリモートのデフォルトブランチより遅れているかをログに出します。
失敗した場合は原因を解消し、再実行が成功してから作業へ進んでください。
Git操作の許可がない読み取り専用の調査では実行しません。
Git操作が許可され、実装に使う適切なworktreeがまだない場合は、Git準備、ログへ出た「ワークツリーの基点」からのworktree作成、絶対パスの報告までに限定した準備依頼として完了させてください。
メインエージェントが進捗の正本をそのworktreeへ移して読み直してから、新しい実装担当を起動します。
すでに適切なworktreeがある場合やGitを使わない場合は、この準備依頼を追加しません。
フォーマット、ステージ、コミットは成果担当へ任せ、成果単位でコミットさせます。
スクリーンショットなどの一時ファイルは、成果担当がコミット前に削除してください。

修正中は変更箇所に近い検証を行い、重い全体検証は段階の成果が揃ってからまとめて行ってください。
高価な外部検証の前に、既存artifact、ログ、代表入力を使って境界相当の安い検証を行わせます。
外部検証で不変条件の漏れが見つかった場合は、次の外部実行より先に安い検証へ追加してください。
Playwrightを使う動作確認は、失敗時の対応も伝えて担当へ任せます。
UI変更では、担当自身にスクリーンショットを見ながら調整させてください。

同じ成果物への差し戻しが2回続くか、同じ受入条件の検証が修正後も失敗した場合は、3回目の局所修正を依頼する前に作業を止め、証拠を一つの原因調査または再設計へまとめてください。
担当を替えても、この差し戻しや検証失敗の回数はリセットしません。
外部操作の一時失敗は、副作用が重複しない場合だけ2回まで再試行し、要求や実装に起因する確定的な失敗には同じ操作を繰り返させないでください。
変更に起因する失敗は、原因と不足していた受入条件を確定してから計画と実装へ戻します。

## 段階末のレビュー

段階末に新しい独立レビュー担当を起動し、確定した指摘を一括で報告させてください。
レビュー担当には、レビュー着手前に対象の設計・実装に適用するスキルを読ませ、関係する規則を成果物の確認観点として使わせてください。
指摘には根拠ファイルと行番号、指摘が成立する条件、実害または要件違反を求めます。
メインエージェントが採否を判断し、必要性が明確で小さい変更は反証を挟まず採用してください。
疑義がある指摘や大規模な変更は、実装担当ともレビュー担当とも異なる第三の担当へ反証を依頼します。
反証には、根拠ファイルと行番号、指摘が成立しない理由を求めてください。

工数や変更規模は対応の妥当性を見直す理由になりますが、バグがない証明にはなりません。
反証の証拠が足りなければ反証不成立とし、それだけで元の指摘を自動採用せず、残る根拠から必要性を判断してください。
判断に必要な根拠が不足する場合だけ、その不足を絞って新しい担当へ調査を依頼します。
どちらでもよい変更は適用不要です。
大規模でも必須の修正なら計画へ戻し、不採用にした指摘も理由を進捗ファイルへ残してください。

採用した指摘はまとめて新しい担当へ委任し、修正後は変更箇所と影響範囲に絞って検証し、必要な独立再確認を行わせてください。
新たな変更、失敗、未解決の懸念がなければ、全体検証や反証と修正を儀式的に繰り返しません。
メインエージェントが採否の判断で読むコードは、報告に含まれる差分・根拠・その周辺の抜粋に限ります。
元ファイルを開くなどの追加の根拠収集は新しい担当へ任せ、自分で調査や検証をやり直さないでください。

## PRと待機

ユーザーが許可した範囲を超えて、GitHubなどの外部サービスの状態を変更してはいけません。
ローカルでも、作業ディレクトリとworktree以外への変更は避け、pnpmやuvなど必要なツールに伴う不可避な変更だけを認めます。
PR作成の指示がある場合は、必要な検証の完了までを依頼の完了条件に含めてください。
PRの本文作成・投稿を担う担当に `contribute-voicevox-github` スキルを使わせます。
ユーザー向けの手順書やPR本文はモデル選択の規則に従ってファイルへ仕上げさせ、メインエージェントは指摘を一括して返してください。
未コミットの作業ツリーを基に既存PRの本文を改める場合は、作業ツリー、公開中のPRのhead、本文で述べる事実を照合させてください。未公開の変更に依存する本文は原稿として完成させ、コード反映が依頼範囲外なら投稿を待ちます。反映が許可されたら検証とpushを終えてから本文を更新し、投稿先の文面を読み戻して原稿と照合させてください。

PR操作を担う担当には、完成した本文ファイル、投稿先、検証結果、readyにできる条件を渡し、PR作成と通常のCI確認まで一つの依頼に含めます。
既存PRへ修正を反映する指示がある場合は、push、PRの状態、通常のCI、競合の確認まで担当の依頼に含めてください。
担当の依頼が完了した後にpushの指示が届いた場合は、新しい担当へこれらをまとめて任せます。
メインエージェントは途中の状態確認やCI待機のためにもGitやghを実行せず、担当の報告を受けて判断してください。
独立したPRはデフォルトブランチへ、コード依存のあるPRはGitHubのstacked PRを使って作成させてください。
PRが未完了の検証に必要な場合はdraft PRを作らせます。
通常のPR CI以外にもマージ判断に影響する検証が残っている間はreadyにせず、必要な検証が成功した場合か、未完了の検証を受け入れるとユーザーが明示した場合だけreadyにしてください。
readyにできるかはメインエージェントが検証結果から判断し、操作はPR担当へ任せます。
PR担当にはURLを報告させ、CI通過とコンフリクトの有無を確認し終えるまで待たせてください。
失敗時は原因を分類し、新しい修正が必要なら新しい担当へ委任します。
readyかつマージ可能な状態を確認できたら、URLとその状態をユーザーへ伝えてください。

外部操作を開始した担当自身に終了まで待たせ、待機のためだけに担当を分けないでください。
作業中は長い `wait_agent` で完了通知を待ち、`sleep`、`list_agents`、短い待機による定期確認を繰り返しません。
追加の判断や新しい情報がある場合、または担当が進行不能になった場合だけ連絡してください。
追加指示で旧計画が不要になった場合は、不要な担当を先に終了します。
待ち時間を埋めるために、完了条件にない改善、追加調査、スキル更新を始めてはいけません。

承認やマージなどユーザーの操作だけを待つ場合は、担当を残さず、再開条件を伝えてターンを終えてください。
ユーザーがマージ監視を明示的に依頼した場合は、その指示を依頼の間保持してください。
監視を依頼されているときは、PR作成を報告した後にマージ開始の連絡を受けた時点で、新しい専用担当に対象PRの完了確認を依頼し、完了まで待たせてください。
マージ開始前に監視担当を待機させません。
監視の依頼をマージの許可と解釈せず、勝手にマージしてはいけません。
ユーザーからマージ完了の報告を受けたら、稼働中の監視担当に確認させ、いなければ新しい担当に一度だけ状態を確認させてください。
マージ確認後は進捗正本と依頼全体の完了条件を照合し、残作業の開始条件を満たすなら追加確認なしで続行してください。
明示的に使っている別のスキルにマージ後の作業がある場合は、その成功後にローカルブランチとworktreeを削除させ、それ以外はマージ後に削除させてください。
削除担当には、対象がこの依頼で作ったものか、worktreeに残すべき変更がないか、PRがマージ済みでローカルブランチの先端がPRのheadと一致するかを確認させてください。
通常削除がsquash mergeで拒否された場合は、承認済みの計画または後続の明示指示で指定されたブランチだけを強制削除させ、許可を取り直さないでください。
担当には削除を承認した計画または指示と確認結果を渡してください。
自動承認審査が拒否した場合は、その承認と確認結果を添えて対象操作だけを一度再試行し、再度拒否されたら別の手段で迂回しないでください。
確認条件を満たさない場合は削除せず、残る差分と判断事項を報告させてください。

内部の担当交代、レビュー継続、経過時間、変化のない状態を逐次報告しないでください。
ユーザーの判断が必要な場合、完了条件やリスクが変わった場合、成果が確定した場合に報告します。
PRや段階の成果は、達成した内容、検証結果、ユーザーの次の操作、判断に影響する残る制約に絞って報告してください。
担当の報告を要約するときは、初出の用語の意味、判断の理由、検証で確認できる範囲をユーザーが理解できるだけ残してください。
完了条件と関係のない未実施事項は列挙しません。
すべての完了条件を満たすか、ユーザーにしか決められない事項を示して待機するまで続けてください。
完了時には、実際の失敗や手間から今後の依頼に役立つ指示が見つかった場合だけ、その指示と理由を伝えます。

このスキルの挙動を検証するときだけ [evals/cases.json](evals/cases.json) を参照し、通常の開発依頼では読み込まないでください。
評価対象には期待する答えを渡さず入力だけを渡し、担当の選択に加えて代表的な模擬実行も確認してください。
