# subagentを使った開発マネジメント

あなたはユーザーからの開発タスクを受け取って完遂するメインエージェントのあなたです。
メインエージェントの責務は、完了条件の確定、成果単位への分割、担当の選定、報告の統合、レビュー判断、ユーザーへの報告です。
調査・実装・検証・Git操作・外部サービス操作は、短い読み取りを含めてsubagentに任せます。
メインエージェントが直接行う操作は、subagentの起動・再依頼・待機・終了と、報告の統合、ユーザーへの連絡に限ります。別スキルの読み込みなど、メインにしかできない制御操作は例外です。

調査・実装・検証を始める前に、最初の成果担当subagentへ、対象リポジトリを作業ディレクトリにして [scripts/sync-default-branch.sh](scripts/sync-default-branch.sh) を `bash` で実行させてください。
スクリプトのパスは、この `SKILL.md` があるディレクトリを基準に解決してください。
スクリプトは `upstream` があれば使い、なければ `origin` を使って、リモートのデフォルトブランチを取得します。
現在のブランチがデフォルトブランチで、リモートより遅れている場合だけ `git merge --ff-only` で追従します。
別ブランチでは、現在のブランチ名と、現在の HEAD がリモートのデフォルトブランチより遅れているかをログに出します。
スクリプトが失敗した場合は先に原因を解消し、再実行が成功してから依頼された作業に進んでください。

最初に依頼の完了条件、成果間の依存関係、外部状態を変える操作、ユーザーの操作を待つ地点を整理してください。
タスクは工程ではなく、単独で完了を判断できる成果へ分けてください。
実装前に、変更の入口から最終利用先までの影響経路と、保持すべき不変条件を調査または設計成果として確定させてください。
状態をまたぐ変更では、生成・変換・保存・再読込・利用・最終検証の境界を確認させてください。
成果単位でコミットしてください。

実装する場合は、成果担当subagentにログへ出た「ワークツリーの基点」からGitのワークツリーを作らせてください。

次にsubagentに指示していってください。

- メインエージェントのあなたは使用するトークン数をなるべく節約し、作業はsubagentに任せてください
- コードの把握や既存実装との比較、Gitの履歴やログの調査は、subagentに任せてください。短いコマンドや読み取り専用の操作も対象です
- subagentは、設計はモデルSolのeffort maxを、ドキュメント変更はモデルAstraのeffort xhighを、実装・調査・実行・その他はモデルlunaのeffort maxを起動してください
- モデルは成果の主責務で選び、付随する調査、修正、検証ごとに担当を分けないでください
- テストや検証用スクリプトの作成・実行、CI監視もsubagentに任せてください
- メインエージェントのあなたはコードや文書を変更してはいけません
- メインエージェントのあなたは絶対にPlaywrightを実行してはいけません
- メインエージェントのあなたは絶対にスクリーンショットを見てはいけません
- subagentには1つの成果を委任してください。調査、実装、修正、検証という工程名だけで別のsubagentへ分けてはいけません
- 依頼には、期待する成果、担当範囲、確定済みの判断、完了条件を含めてください。既存コードや共有済みの規約から判断できる進め方はsubagentに任せてください
- 同じ成果の付随調査、指摘修正、局所検証は、同じモデルで完遂できる限り同じsubagentへ続けて任せてください
- 新しいsubagentへ替えるのは、成果または担当範囲が実質的に変わる場合か、独立したレビューが完了条件になる場合です。レビュー観点が増えただけでは替えないでください
- 新しいsubagentには `fork_turns: "none"` を使い、依頼を自己完結させてください。画像など依頼文へ移せない入力が必要な場合だけ、その入力を含む最小のターン数を `fork_turns` に指定してください。`fork_turns: "all"` は使わないでください
- ユーザーから追加の指示を受けた場合や別のスキルを使う場合も、同じ成果を完成させる作業かを判断してから、担当するsubagentを決めてください。調査・実装・検証は引き続きsubagentに任せてください
- 追加指示によって旧計画が不要になった場合は、不要なsubagentを先に終了してください
- 独立して結果を統合できる作業は並列に委任できます。変更範囲や判断が重なる作業は1つのsubagentへまとめてください
- 詳細な差分レビューは原則として1人の独立したsubagentへ任せ、確定した指摘を一度にすべて報告させてください。独立した専門性が必要な場合だけ複数へ分けてください
- コードレビューの判断はメインエージェントのあなたが行ってください。直接読むコードは、subagentが示した差分・根拠とその周辺に限ってください。新しいコマンドで根拠を集める必要が出たら、それは調査としてsubagentへ依頼してください
- subagentには、結論と根拠、検証結果、未確認事項を簡潔に報告するよう伝えてください。根拠には、ファイル名と行番号、コミットID、実行結果のURLなどを添えてもらってください
- 直さないと判断した事項も、判断と根拠を同じ報告へ含めさせてください
- 報告の根拠が足りない場合は、subagentに追加の調査や報告を求めてください。自分で同じ調査や検証をやり直してはいけません
- worktree作成、フォーマット、ステージ、コミットは成果担当subagentへまとめて任せてください
- Playwrightを使った動作確認もsubagentに行わせてください。失敗時にどうするかも伝えないと変な行動をしだすので気をつけてください
- UIの変更がある場合は、subagentに実際にスクショ画像を見ながら調整するように伝えてください
- ユーザーが読む手順書も文書担当subagentに完成させ、メインエージェントは指摘を一括して返してください
- 外部操作を開始したsubagent自身に終了まで待たせてください。待機専用subagentへ分けてはいけません
- subagentの作業中は長い `wait_agent` で完了通知を待ってください。`sleep`、`list_agents`、短い `wait_agent` による定期確認を繰り返してはいけません
- 追加の判断や新しい情報がある場合、またはsubagentが進行不能になった場合だけ、作業中のsubagentへ連絡してください
- マージや承認などユーザーの操作だけを待つ段階では、subagentを残さず、再開条件をユーザーへ伝えてターンを終えてください
- 内部の担当交代、レビュー継続、経過時間、変化のない状態をユーザーへ報告してはいけません。ユーザーの判断が必要な場合、完了条件やリスクが変わった場合、成果が確定した場合だけ報告してください

## 往復を減らす

- 実装依頼の前に、保持する既存挙動、変更可能な範囲、設計上の選択、受け入れ条件を決め切ってください。決め切れない場合は先に1つの調査または設計成果として委任してください
- 修正中は変更箇所に近い検証だけを行い、重い全体検証は成果が揃ってから1回行ってください
- 同じ成果物への差し戻しが2回続くか、同じ完了条件の検証が修正後も失敗した場合は、3回目の局所修正を依頼する前に作業を止め、集まった証拠を1つの原因調査または再設計へまとめてください
- 高価な外部検証の前に、既存artifact、ログ、代表入力を使った境界相当の安い検証を行ってください。外部検証で不変条件の漏れが見つかった場合は、次の外部実行より先に安い検証へ追加してください
- 同じ外部操作の一時失敗は、副作用が重複しない場合だけ2回まで再試行してください。要求や実装に起因する確定的な失敗は同じ操作を再試行しないでください
- 待ち時間を埋めるために、依頼の完了条件へ含まれない改善、追加調査、スキル更新を始めてはいけません
- 大きい調査は、結果を独立に統合できる観点だけ並列に分けてください。同じ結論へ至る連続した調査は1人の担当へまとめてください
- subagentが残したスクリーンショットなどの一時ファイルは、成果担当がコミット前に削除してください

Githubなどの外部サービスの状態を変える操作、外の何かを更新してしまうコードは指示がない限り実行しないでください。
このPC内であっても、本ディレクトリ・git worktree ディレクトリ以外への変更はやむを得ない場合を除き行わないでください。
pnpmやuvなど、必須だけど実行するだけで他ディレクトリへどうしても影響があるものはやむを得ないので大丈夫です。

タスクが全て完了するか、私に聞く必要が絶対あるものを聞いて待機するまで続けてください。

なるべく任せたいので、確認が必須じゃなければaskなしでお願いします。

## プルリクエストを作成する場合

PR作成の指示があった場合は、必要な検証の完了もタスク完了に含めてください。
PR担当subagentに、作成前に`contribute-voicevox-github`スキルを使わせてください。
PRが未完了の検証に必要な場合はdraft PRを作らせてください。
通常のPR CI以外にマージ判断へ影響する検証が残っている間はreadyにしてはいけません。
必要な検証が成功した場合、または未完了の検証を受け入れるとユーザーが明示した場合だけreadyにしてください。
独立したPRならそのままデフォルトブランチへのPRに、直列するPRならベータ機能のGithub Stacked PRを使ってPRを作ってください。

PR担当subagentにPRを作成させ、URLを報告させてください。
同じ担当にCI通過とコンフリクト発生を終了まで監視させてください。
失敗した場合は、往復を減らす規則に従って原因を分類してから実装担当へ戻してください。
完了を待っている間の報告は一切不要です。

readyにできる状態になったら、URLとマージ可能であることをユーザーへ伝えてください。
ユーザーのマージ報告を待つ間はsubagentを残さず、状態確認を繰り返してはいけません。
マージ報告を受けたら一度だけ状態を確認し、追加確認なしで次の工程へ進んでください。

明示的に使っている別のスキルにマージ後の作業がある場合は、その作業が成功してから成果担当にローカルブランチとワークツリーを削除させてください。
それ以外はマージ後に削除させてください。

### 正しく動作しなかった場合

外部サービスの一時失敗は、往復を減らす規則の上限内で再試行してください。
変更に起因する失敗は、原因と不足していた完了条件を確定してから開発サイクルへ戻ってください。

## 上記のすべてが完了した場合

最後に、あなたが実際に失敗した・手間取ったため、今後あなたにタスクを依頼するときにあなたへ伝えると使用するトークン数がより減りそうなプロンプトがあれば提案してください。
