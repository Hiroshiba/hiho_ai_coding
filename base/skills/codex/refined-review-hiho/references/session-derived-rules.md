# セッションから確定した規則

## ストリームの先読みを確認する

- 適用条件: ストリーム変換が最初の要素や直前の要素を保持し、次の要素を取得してから処理する変更
- 確認事項: 最初の出力に次の入力が必要か、終端 API が空入力による明示的なフラッシュを許すか、最初の要素から得る設定が型や既定値ですでに固定されていないかを確認する
- 指摘条件: 不要な一要素先読みで初回出力が遅れ、空ストリームでも失敗し、安全な終端処理で先読みを除ける
- 理由: ストリーミング API の応答開始が入力生成一回分遅れ、空入力のエラー経路も増える
- 重大度: 原則として修正推奨。公開された遅延要件や正しさを破る場合だけ修正必須
- 例外: 最終の非空要素と同時に終端フラグを渡す必要がある、空入力が拒否される、実行時設定を最初の要素から得る必要がある、非空入力が契約で保証される場合は指摘しない

不要な先読みと空ストリームでの失敗が同じ原因なら、一件の指摘へまとめる。
呼び出し元が空ストリームを渡すか未確認の段階では、空入力の失敗だけを独立した修正必須にしない。

python-soxr を使う場合は、リポジトリが固定するバージョンを確認する。
最終チャンクで `last=True` を渡すことと、空配列を最終入力にできることを別々に確認する。
後者が固定版の実装だけで確認できる場合は、公式文書の保証と書かない。
空配列でのフラッシュを修正案に使うコメントでは、公開文書ではなく固定版の実装で確認した挙動だと分かるようにする。

空入力が終端通知だけのために置かれているとコードから読み取りにくい場合は、短い NOTE コメントを求める。
説明は手順を繰り返さず、例えば次の程度にする。

```python
# NOTE: 最後の出力を空配列でフラッシュする
```

## テストを所有レイヤーで確認する

- 適用条件: API 経路や統合テストの不足を指摘しようとするとき
- 確認事項: 変更された挙動を所有する関数や層、既存の E2E と単体テストの責務分担、追加テストが実際に検証する条件を確認する
- 指摘条件: 変更された層のテストでも、層をまたぐ配線や公開契約のテストでも重要な挙動が検証されていない
- 理由: テスト種別の名前だけで不足を判断すると、既存方針に反する重複テストを要求して誤検出になる
- 重大度: 未検証の不具合リスクに合わせる。E2E がないこと自体では上げない
- 例外: 純粋な後処理を単体テストで十分に検証し、API の E2E が疎通だけを担当する構成なら、同じ条件の E2E 追加を求めない

## 共通化で共有された責務を確認する

- 適用条件: PR が重複解消、共通化、TODO の解消を目的とするリファクタリング
- 確認事項: 変更前後で重複する実装や分岐が実際に減ったか、新しいヘルパーがどの責務を一か所へ集約したか、TODO の文面と達成範囲が一致するかを確認する
- 指摘条件: 分類名やラッパーだけを揃え、対象だった処理と分岐が別々に残るのに、共通化済みとして TODO を削除する
- 理由: 抽象化だけが増え、将来の二重修正という元の危険が残る
- 重大度: 原則として任意。片側だけの修正で既知の不具合が起きる場合は修正推奨
- 修正方向: 実際に共有できる責務へ変更を狭めるか、未解決の TODO を残す
- 例外: 異なるバックエンド実装を残しながら、処理順や適用条件という共有方針を一か所へ集約することが明示された目的なら、実装が別であることだけを理由に指摘しない

## 追加された CSS を現在の要件へ結び付ける

- 適用条件: UI の不具合修正で CSS 宣言やユーティリティクラスを追加する変更
- 確認事項: 各追加指定について、現在の DOM、入力データの契約、レイアウト規則から、どの条件で表示を変え、どの要件を満たすかを一つずつ確認する
- 指摘条件: 現在の要件へ寄与せず、発動条件が現在の契約では成立しないか、意図されていない表示方針を将来の入力へ追加する指定
- 理由: 修正に必要な指定が見えにくくなり、意図しない表示方針を実装上の契約として残す
- 重大度: 原則として任意。現行入力で見切れや操作不能を起こす場合だけ影響に合わせて上げる
- 修正方向: 要件に必要な指定だけを残す。単純な削除なら、現在不要な理由を一文で書いた suggestion を使う
- 例外: 現在サポートする入力や画面幅で発動し、明示された表示要件か既存のデザイン規則を満たす指定は指摘しない

画像の `object-fit: cover` は、入力画像と表示枠の縦横比が異なり得るか、切り抜く意図があるかを確認する。
入力契約が表示枠と同じ縦横比で、切り抜く意図もない場合は、将来への防御だけを理由に追加しない。

Flex アイテムの縮小禁止は、負の空き領域が生じ、アイテムが目的の寸法より縮み得るかを自動最小サイズまで追う。
実表示の観測だけで必要性を判断せず、現在の DOM と CSS の規則から発動条件が成立しないと確認できた場合だけ指摘する。

## 閉じた型の対応をコンパイル時に網羅する

- 適用条件: TypeScript の閉じた union や enum の全要素を、別の値へ対応させる処理を追加または変更する場合
- 確認事項: 元の型へ要素を追加したとき、対応表の更新漏れがコンパイルエラーになるかを確認する
- 指摘条件: 配列探索などを使っているため、現在の要素は揃っていても将来の追加漏れを型検査で検出できない
- 理由: 新しい要素が実行時の例外や検証漏れになるまで、対応表の不足を発見できない
- 重大度: 現在の要素がすべて正しく対応している場合は任意。現在到達できる要素が欠けている場合は影響に合わせて修正推奨以上にする
- 修正方向: `satisfies` を使う `Record` か、到達不能分岐を持つ網羅的な `switch` にする
- 例外: 実行時に要素が追加される拡張点など、元の集合が閉じていない場合は指摘しない
