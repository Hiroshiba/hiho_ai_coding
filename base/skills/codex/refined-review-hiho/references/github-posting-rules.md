# GitHub 投稿文の規則

PR タイトル、PR 本文、レビュー後の変更を説明する通常 PR コメントを作成または修正するときだけ適用する。
レビューコメントやレビュー報告の構成と文体には適用しない。

## タイトルを Conventional Commits 形式にする

- 適用条件: PR タイトルを作成または修正する場合
- 書くこと: 変更の主目的に合う Conventional Commits の type とコロンを先頭に置き、その後へ変更内容を書く
- type の選び方: CI や配布自動化なら `ci:`、不具合修正なら `fix:` のように、変更の主目的とリポジトリの用法に合わせる
- 書かないこと: type のないタイトルや、変更内容と一致しない type
- 例外: ユーザーが別の形式またはタイトルを明示した場合は、その指定を優先する

例えば、開発版 Release への公開を自動化する変更なら「開発版 Release へ生成物を公開する」ではなく、「ci: 開発版 Release への継続デプロイを追加」と書く。

## タイトルに操作範囲を書く

- 適用条件: 変更が特定の画面、欄、操作経路だけに作用する場合
- 書くこと: 操作と、その操作が有効になる対象をタイトルへ含める
- 書かないこと: アプリ全体で有効になったと読める、対象を省いた表現
- 例外: 実際にアプリ全体へ作用する変更では、存在しない対象を足さない

例えば、変更がインポート欄だけに作用するなら「ファイルをドラッグ＆ドロップで読み込めるようにする」ではなく、「インポート欄へドロップしたファイルを読み込めるようにする」と書く。

## PR の概要は実装を知らなくても分かるように書く

- 適用条件: PR の概要を説明する文章
- 書くこと: 変更の目的、対象、結果を、実装の詳細を知らない読者にも分かる言葉で書く
- 書かないこと: 内部実装自体が PR の目的でない限り、コンポーネント名、イベント名、型名などの実装用語や識別子を概要へ含めること
- 書かないこと: 問題を起こす値を採用しないなど、修正内容から当然に分かり、別の結果を説明しない実装上の前提
- 文量: 一文で足りる説明を、同じ結果を言い換える複数文にしない
- 例外: 内部実装そのものが PR の目的である場合は、必要な技術用語を残す。ただし、識別子だけで説明を完結させず、何をどう変えるかを書く

実装の選択理由が必要なら概要へ重ねず、経緯や判断理由を説明する文章へ分ける。

## 差分から明らかな実装説明を省く

- 適用条件: PR 本文へ変更内容を載せようとする場合
- 書くこと: 変更の目的、対象、利用者や運用上の結果を概要として残す
- 書かないこと: ファイル形式、処理手順、ガード、権限設定など、差分からそのまま読み取れる実装変更。箇条書きから文章へ変えて残すこともしない
- 書かないこと: 概要で説明済みの目的や結果を、変更内容の節で言い換えること
- 見出し: 書くべき内容が残らなければ、変更内容の見出しごと削除する
- 例外: 複数の独立した利用者向け結果を伝える場合や、差分だけでは分からない判断理由を説明する場合は、必要な項目だけを書く

## 確認コマンド一覧を省く

- 適用条件: PR 本文へ実行した確認を載せようとする場合
- 書かないこと: lint、型検査、ビルドなど、成功した確認コマンド名の一覧やチェックリスト
- 見出し: テンプレートに確認の見出しがあるだけでは記載を求められたと判断せず、書くべき内容がなければ見出しごと削除する
- 例外: ユーザーやリポジトリの指示が、確認項目を具体的に記載するよう明示している場合は、その指定に従う
- 例外: 失敗や未実施がレビュー判断へ影響する場合は、コマンド一覧ではなく、確認できていないことと影響を書く

## 概要と具体例を段落で分ける

- 適用条件: PR の概要に加えて、一つ以上の具体例を書く場合
- 書くこと: 概要を最初の段落で完結させ、具体例を次の段落へ置く
- 改行: 複数の具体例を文章で並べる場合は、一文ごとに改行する
- 書かないこと: 概要と具体例を同じ段落へ併記すること
- 例外: 具体例が不要な短い概要では、段落を増やさない

## 経緯や判断理由では根拠と変更方針の因果を続けて書く

- 適用条件: PR の経緯や判断理由を説明する文章
- 書くこと: 原因や制約として確認した事実と、その事実に基づく変更方針を別の内容として書く。変更方針には、何を変えるかだけでなく、その変更が原因へどう作用するかも含める
- 文と段落: 一つの原因から一つの変更方針を説明する場合は、条件と起きる問題を一文にまとめ、その直後へ変更方針の文を置く。二文が長ければ、空行を挟まず文の間で改行する。残る制約は次の段落へ分ける
- 書かないこと: 根拠と変更方針を長い一文へ詰め込むこと、二つを空行で別の段落へ離すこと、根拠だけを書いて変更との関係を省くこと、実行する処理だけを書いて期待する効果を省くこと
- 例外: 根拠と変更方針の関係が短い一文で明らかなら、文や行を増やさない。独立した複数の判断は、一組ずつ段落を分けてよい

根拠には、現行の挙動、仕様、関連議論、制約、固定版依存などがある。
外部ライブラリやフレームワークの契約を根拠にする場合は、リポジトリが固定するバージョンで確認し、公開文書の保証と固定版の実装を区別する。

## 関連資料は変更との関係と参照先への有用性で選ぶ

- 適用条件: PR 本文や通常 PR コメントへ Issue、コメント、PR、Actions run などのリンクを載せる場合
- 確認事項: 資料の本文まで読み、扱う原因、要件、合意された方針、解決内容のいずれが PR とつながるかを確認する。Issue や PR への参照では、通知や被参照記録が参照先の読者に役立つかも確認する
- 書くこと: PR が解決する課題、従う議論、前提とする変更など、本文から関係を説明できる資料だけを載せる。Issue や PR へのリンクは、その課題を実際に解決する場合や、合意された変更の共有が相手の対応に役立つ場合に残す
- 書かないこと: 症状が同じだけの Issue、調査対象になっただけの Issue、診断で確認しただけの Actions run、関係を説明しないリンク。変更の観測例や発見のきっかけにすぎず、参照先の読者に有用な情報がない Issue や PR へのリンクも載せない
- 見出し: 条件を満たす資料がなければ、関連資料の見出しごと削除する。「なし」で埋めない
- 例外: 調査資料が変更方針の理解に必要な場合は、確認した事実と変更との関係を文章で説明する。Issue や PR へのリンクは、この場合も参照先の読者への有用性を満たすものだけにする

表面上の症状が同じでも、原因、要件、解決方針が異なる資料は直接関係するものとして扱わない。
リンクを省く場合、`#番号` などの被参照記録を残す表記へ置き換えない。

## 発見のきっかけは観測した事実だけを書く

- 適用条件: PR を作るきっかけになった出来事を本文へ残す場合
- 書くこと: 実際に観測した挙動を変更内容と分け、「その他」などの補足欄へ短く書く
- 書かないこと: 直接関係しない Issue や調査資料の紹介、原因や解決策の比較、求められていない発見経緯
- 例外: 資料との比較自体が変更方針の理解に必要で、その関係を本文で説明できる場合は、経緯や判断理由として書く。Issue や PR へリンクするかは、関連資料と同じ基準で判断する

## 指定された文章作成スキルを再適用する

ユーザーが文章作成スキルの使用を明示した場合、PR 投稿文を修正して再提示または投稿するたびに、そのスキルを再適用する。
以前の版へ適用した結果を、修正後の版へ流用しない。

## 通常 PR コメントは作者へ説明が必要な判断へ絞る

- 適用条件: レビュー後に作者のブランチへ加えた変更を、通常 PR コメントで作者へ説明する場合
- 書くこと: 相談せず加えた判断を伴う変更について、変更と理由を一つの短い箇条書きへまとめる。ユーザーが文体を示した場合は、その語調に合わせる
- 語調: 仕様や依頼で確定していない裁量的な変更は、正解として断定せず、試した意図が伝わるように書く
- 書かないこと: 主な変更を支えるセレクターや無効状態の除外、明らかなコメント整理、CI の結果、Issue の関連付けなど、作者の判断や対応を必要としない作業の全件一覧
