# 目的

変更が新たに生む具体的な問題だけを、作者がコメント単独で理解できる形で報告する。
好み、未確認の推測、既に別の場所で扱う課題で指摘数を増やさない。

# レビューの進め方

1. PR の目的、関連 Issue、既存コメント、作者と依頼者が示した対象範囲を確認する。
2. 差分で変更範囲を把握し、指摘の根拠には最新 HEAD の実コードを使う。
3. 呼び出し元、データの流れ、境界条件、エラー経路、リソース寿命を追って指摘候補を作る。
4. 既存テストの責務分担と変更箇所の所有レイヤーを確認する。
5. 外部ライブラリの挙動へ依存する候補は、固定されているバージョンの資料で確認する。
6. 各候補が今回の変更で発生または悪化したことを確認してから報告する。

Python のストリーム処理、テスト追加の要否、共通化や TODO の解消、UI 修正で追加された CSS の必要性、TypeScript の閉じた型の対応をレビューするときは、[セッションから確定した規則](references/session-derived-rules.md)を読む。
該当しない変更では読まない。

レビューに続いて PR タイトル、PR 本文、レビュー後の変更を説明する通常 PR コメントを作成または修正するときは、[GitHub 投稿文の規則](references/github-posting-rules.md)を読む。
レビューコメントやレビュー報告には適用しない。

# 指摘の選別

次をすべて満たす候補だけを指摘する。

- 実コードまたは明示された仕様から再現条件を説明できる
- 今回の変更が原因か、今回の変更で影響が広がる
- 利用者影響、誤動作、性能低下、保守上の具体的な危険のいずれかがある
- 既存コメントと重複せず、最新 HEAD でも未解決である
- 修正方向を示せる

関連 Issue で扱うと明示され、今回の変更がその問題を悪化させない課題は指摘しない。
問題が残っているという理由だけで PR の対象へ戻さない。

未確認の候補を「要確認」として報告しない。
確認できない重要事項がある場合は、指摘と分けて調査上の制約を述べる。

# 根拠の扱い

外部ライブラリの挙動は次を区別する。

- 公開 API や公式文書が保証する挙動
- 固定バージョンの実装から確認できる挙動
- 手元の実験で観測した挙動

実装確認や実験だけの結果を、公式文書で保証された仕様として書かない。
ソースを示す場合は、ブランチ先端ではなく固定バージョンかコミットへリンクする。
補足が長い場合だけ、結論を先に一文で書き、詳細な根拠を HTML の `details` へ入れる。

# コメントの書き方

指摘は重大度が高い順に並べる。
各指摘には、対象位置、発生条件、具体的な影響、修正方向を含める。

コメント先が問題のある行と異なる場合や、変更によって差分外の行が不要になった場合は、どの変更が何を引き起こしたかを本文へ書く。
行の位置や先行する会話を知らない読者にも、コメント単独で因果関係が伝わるようにする。

未使用値や形式違反を指摘するとき、静的解析の設定や実行結果を確認していなければ、静的解析が失敗すると断定しない。
確認できた事実と修正方向だけを書く。

GitHub の suggestion は、変更対象行へ正確に適用できる場合だけ使う。
差分外の変更を近くの行へ無理に suggestion として置かない。

直接投稿するインラインコメントでは、依頼されない限り重大度や自信度を本文へ混ぜない。
レビュー報告では次の基準を使う。

- 修正必須: 誤動作、データ損失、セキュリティ問題、公開契約違反に直結する
- 修正推奨: 再現可能な性能低下、境界条件の欠陥、将来の不整合を生む設計上の問題がある
- 任意: 挙動を壊さない保守性、命名、文書の改善である
- Nit: 意味や一貫性への影響がほとんどない表記上の改善である

確信度の高さや修正の容易さを理由に重大度を上げない。
型が許すだけで実際の呼び出し契約が未確認の入力を、公開契約違反と断定しない。

# 出力

最初に指摘を列挙する。
指摘がなければ「指摘はありません」と明記する。
要約や未検証事項は、指摘の後に必要な場合だけ短く書く。

レビュー依頼は読み取り専用として扱う。
明示されない限り、コード変更、コメント投稿、レビュー送信、PR 操作は行わない。

複数のインラインコメントを直接投稿するよう明示された場合は、すべてのコメントを一つのレビューに含め、レビュー送信を一度だけ行う。
個別投稿を明示された場合だけ、一件ずつ送る。
別途依頼された通常コメントはレビューへ混ぜず、通常コメントとして投稿する。
