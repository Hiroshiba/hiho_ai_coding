# 既存の処理関係から実装の細部を決める

## 揃える既存実装を、挙動と責務から選ぶ

類似実装は、採用した構文ではなく実現したい挙動から探せ。同じ目的を別の方式で実現する例も集め、表示条件・操作性・責務の違いを対応付けて、移せる範囲を判断せよ。
方式の傾向は同じ構文の使用件数で判断せず、両方式を選べる箇所の例で比べよ。内部要素なので方式が限られる例は分けて数えよ。
見た目の表現を揃える場合は、役割が近い既存例と文字サイズ・太さ・色・余白を別々に照合せよ。mixin は付随する指定まで確かめ、必要な差だけを採る案と比べよ。
自分が追加した指定や、新設したファイル内の自分の書き方を前例に数えるな。

先行変更の上に差分を重ねる場合は、先行変更を含む比較と追加する差分を分け、先行側で削除・整理した処理を戻していないか確かめよ。
既存との一致を優先し必須の変更だけを求められた場合は、残す差ごとに、揃えると成立しない要求や入力条件を示せ。必須でない拡張や追加対策は実装へ混ぜず、利点・残る制約・変更量を添えて最後に提案せよ。

別 OS などに同種の処理がある場合は、処理結果だけでなく、workflow とスクリプトの責務分担、環境変数の設定とリセット、一時パスを渡す位置、出力コマンド、条件式の順序を対応付けよ。既存側を基準にする依頼では、既存側を新しい側の書き方へ変えて差を消すな。
値の名前や順序を揃える場合は、対象の識別子を検索し、setup の入力、後続 step への書き出し、cleanup のリセット、再 setup など、その値群を並べる全ブロックを一覧にして相対順序を比べよ。
順序が挙動に影響しない箇所の漏れは実行検証では見つからず、未変更のブロックは差分にも現れない。変更前後の順序表で全ブロックを確かめよ。異なる順序を残すなら処理上の必要性を示せ。

## 方式の置き換えは、変えない案と比べて決める

既存方式で要求を満たせる状態から別方式への置き換えを検討する場合は、何も変えない案、必要な接続だけを変える案、方式ごと置き換える案を、合格条件・変更量・残す責務・新たに引き取る責務・利用者が示した優先順位で比べよ。
コードが短くなる、公開 API を使える、処理をまとめられるといった利点が一つあっても、それだけで採用を推奨するな。置き換えないと要求や回避必須の不具合を満たせないか、利点が変更量と失う一貫性を上回る場合だけ実装へ含め、それ以外は任意の提案に分けよ。
変更後のコードが整合しテストに通ることは、変更前の方式も同じく合格するなら採用の根拠にならない。
利用者が選択肢を許容した、関心を示しただけの発言を、採用の指示とみなすな。

現行実装は今そう動く事実の根拠であって、その方式を残す必要性の根拠ではない。必要性を問われたら、要求・外部制約・導入経緯を確かめ、同じ要求を満たす代替案と比べよ。

## 変更の目的を、省略経路まで含む合格条件に置き換える

処理の一部更新・移行・再利用を実装する場合は、作業前に、変える結果と変えてはいけない結果について、比較する入力・期待する値・観測する箇所を決めよ。
呼び出し削減が目的なら、呼び出し数と、無関係な判定や通知が変わらないことを別々に確かめよ。
待機や操作の回数削減が目的なら、最終状態ではなく、操作・待機・次の操作の順序を合格条件にせよ。経路を統一した結果、長い待機の後に操作が戻るなら、最終結果が同じでも目的を満たしていない。

確認する経路は利用者の例だけで決めず、通常の入口から分岐を追え。一部更新、失敗・延期、外部呼び出しだけの省略、処理全体の省略、保存後の再利用のうち目的に関係する経路ごとに、更新する値・保持する値・下流へ渡す値を対応付けよ。
保持を確かめる値は、移行後に残った値や既知の不具合例からではなく、変更前に使われていた値から洗い出せ。判定が依存する関連候補や確定情報も照合し、正当な更新・取消と適用漏れを分けよ。
許可された実データのコピーがあれば、本番と同じ正規化・識別子付与・対象選別・入力生成に通し、判定から保存・再読込まで確かめよ。手作りの中間入力で失敗した場合は、本番の生成経路でも成立する入力か確かめてから修正の根拠にせよ。
型検査、保存値の存在、正常終了は保持の保証にならない。確認した入力と経路、未確認の経路を分けて報告せよ。

## 非同期処理の順序と完了条件を分ける

初期化や起動処理の await を判断する場合は、状態の書き込み元から後続の読み手へ追い、処理内部の順序、呼び出し元の完了契約、失敗の伝播先を分けよ。呼び出し元が void であることを理由に、関数内部の状態待ちや末尾の拒否伝播まで外すな。
通知を待機条件に加える場合は、送信 API から受信ハンドラーまで追い、返信が受付・表示命令・描画のどこまでを保証するか確かめよ。DOM の途中表示を観測する E2E を、OS の画面への描画完了待ちの要件へ読み替えるな。

複数要素へ非同期処理を行う場合は、要素ごとに A の完了後に B を始める順序と、全要素の A の完了後に B を始める同期点を区別せよ。`Promise.all` と反復処理の入れ子から実際に開始しうる順序を列挙し、遅い要素や失敗する要素があるときに別要素の B が始まるか確かめよ。
どちらが必要かは途中結果を使う側から決めよ。要素内の順序を確かめただけで、全体の同期順序も保ったと報告するな。

## 型・関数・名前を、使われ方と周囲に合わせる

型だけのファイルを作る・維持する場合は、型の利用先と責務を調べよ。一つの処理の引数契約を呼び出し側も参照しているだけなら、複数ファイルから使うという理由で独立させず、その処理のモジュールに置けるか確かめよ。
直和型の選択肢が同じ付随データを持ち、違いが識別値だけなら、`{ mode: "none" } | { mode: "copy" | "move"; directory: string }` のように識別値をまとめてデータを一度だけ定義せよ。

関数の配置、戻り値注釈、docstring とコメントの句点は、既存ファイルの同種の箇所と照合せよ。補助関数と default export の位置、省略可能な `void` の扱いも対象にせよ。
短いオブジェクト・型・関数呼び出しは、周囲に合わせ、フォーマッターが保つなら一行にまとめよ。CSS の基本指定と状態による指定のように関心事が変わるまとまりは、周囲に合わせて空行で分けよ。コメントの有無を区切りの判断条件にするな。

一つの概念の名前を直す場合は、型、生成する関数、使う関数、変数、外部設定名、docstring を呼び出し経路に沿って照合せよ。配置元だけでなく方法も含む型を `Source` と呼ぶなど、名前が扱う範囲を狭く見せていないか確かめよ。ただし `source`・`destination` のように別の役割を正しく表す名前まで機械的に置き換えるな。
値の有無を調べる名前は実在確認と区別せよ。パスを組み立てて返す関数は、同種の既存関数の動詞に合わせよ。

IPC やイベントに対応する公開 API は、通知を送る関数とハンドラーを登録する関数を分け、同じ方向と目的の既存の組を基準に名付けよ。IPC 名に `ON_` があるだけで送信 API に `on` を付けるな。
既存の傾向を件数で示すときは、今回の追加を除き、分類対象と分母を示せ。

文書で製品やモジュールの略称が同じ説明中の別概念と重なる場合は、正式名称や修飾語で区別せよ。例えば CPU の P/E コアと並べて書くときに VOICEVOX CORE を「コア」とだけ呼ぶな。一括置換で別概念の語やコード上の識別子まで変えるな。

配置先の一部だけに使う値は、設定項目全体を表す名前ではなく、「実行ファイルと同じディレクトリ」のような配置の意図で名付けよ。固定の接頭辞を選んで連結するだけなら、長い名前の関数を作るより、意図を表す定数と連結で読めるか確かめよ。
同じ配置意図の箇所には、ある OS で接頭辞が空でも同じ値を使い、別の配置が必要な分岐は分けよ。

## CSS の対象と各指定の必要性を確かめる

自前の要素、直接配置した部品のルート、部品が内部生成する要素を分け、通常の scoped CSS が届く対象まで `:deep` にまとめるな。
役割を指定するクラスは既存のスコープで足りる名前にせよ。汎用の部品クラスで同じ役割を指定している参照は、配置・表示切替・通常時の非表示まで追って揃えよ。

幅を決める場合は、同じ目的の既存表示と単位・値の粒度を照合せよ。実測の最小値へ細かく合わせる前に、周囲になじむ候補を必要なフォント・桁数で比べ、収まることと見た目の採否を分けよ。一度選んだ調整値を全体の規約へ広げるな。

追加する各宣言と条件について、外した場合に効く既存指定・ライブラリの指定・初期値と、現在の DOM で変わる表示を対応付けよ。計算値が変わっても位置や幅が変わるとは限らない。複数を削る場合は、まとめて削った結果も確かめよ。
SCSS のネストやセレクターを整理する場合は、生成 CSS の対象要素・スコープ属性・詳細度・宣言・出力順を照合せよ。コンパイル成功だけで同等とせず、静的に同等と確かめられる整理なら追加の画面確認は求めなくてよい。

配置や表示切替を検証する場合は、枠の幅だけでなく、切り替える値と操作部品それぞれの位置と可視状態を確かめよ。要素なし、非表示、ホバー、キーボードフォーカスのうち関係する状態を同じ条件で比べよ。

## テストの境界と構造を、検証する責務へ合わせる

入力検証のテストは、値を拒否する責務がどこにあるかと、プロジェクトのテスト方針を先に対応付けよ。
Pydantic の Field や FastAPI の Query のように宣言だけで検証が完結する制約をライブラリに任せる方針なら、API の負例を消したあと同じ値域をモデル単体テストへ移すな。独自 validator や複数項目の組合せ判定は、API 固有の応答を確かめる目的が別にない限り、モデルを直接構築する単体テストで確かめよ。

同種テストは、ファイル名や配置だけでなく、対象を直接構築するテスト、同じ例外型、同じ種類の validator で探せ。最も近い例と、配置・ファイル名・補助型・基準入力の生成・例外の確認・クラスの有無を揃え、残す差は対象の入力と責務から必要なものに絞れ。

既存 E2E へ自動経路や環境分岐を加える場合は、分岐固有の操作と途中確認だけを分け、共通の画面取得と完了条件は共有せよ。意味が変わらない step 名を改名したり、既存の検証を別の途中表示へ置き換えたりするな。
イベント待機は発火より前に登録せよ。登録時点から個別期限が進むかを採用版の API と設定で確かめ、長い前段処理を含めても全体期限内の正常経路が失敗しないか照合せよ。個別期限を無効にするのは、有限の全体期限があり、個別期限自体が要件でない場合に限れ。
途中表示を locator で確かめる場合は、表示元の DOM、状態遷移、同じ文言を含む操作部品を照合し、何を観測する assertion か確定せよ。自動待機は開始前に消えた表示を拾わない。指定された途中確認を黙って削らず、対象環境でその経路が実際に実行されたか確かめよ。

テストを追加する価値と、今回の変更に含めるかは別に決めよ。利用者が必要性を認めつつ今回は外すと決めたら、技術的な価値を理由に差分へ残さず、指定された PR コメントや後続課題へ回せ。

## 入力の補完・検証・変換を分ける

複数の入力から動作を決める処理を簡略化する場合は、未指定・空文字・有効値・不正値の組合せごとに、受理か拒否かと返す値を先に整理せよ。維持する条件と変えてよい条件を分け、過去のフォールバックや出力形をすべて保つ前提だけで「これ以上簡単にできない」と結論するな。
既定値が必要だと説明するときは、明示値では成功し未指定時だけ失敗する最小の入力例を示し、必要な振る舞いと特定 API の必要性を分けよ。

短い検証関数は、未指定値の補完を先に済ませ、許される組合せを同じ形の分岐で並べよ。前の分岐の否定を読み解かないと次の正常条件が分からない構造は、数行短くても避けよ。
Zod へ集約する場合は、既存関数を長い `transform` へ移しただけで簡潔になったとみなすな。許される組合せを object の union で表せるか、検証と変換を分けられるかを確かめよ。型はスキーマから導出して手書きの型を残さず、不要なプロパティの除去とリテラル型の絞り込みも確かめよ。
同じ実行内で検証済みの値を直接渡す箇所に、型を置くためのスキーマや重複した parse を足すな。

未指定を無効とする真偽値の環境変数は、入力境界で受理する文字列を限定し、未指定を無効として補って `boolean` へ変換せよ。`"true" | "false" | undefined` を下流へ持ち込まず、外部ライブラリが求める特殊値は設定へ渡す箇所で対応付けよ。
workflow が決める動作を外部ライブラリへ渡す場合は、似た名前の標準環境変数や CLI 指定があることだけで選ぶな。採用版での意味が目的と違うなら、プロジェクトの真偽値を設定境界でライブラリの値へ変換し、正式処理・無効時・ローカルで未指定の場合を比べよ。

## 採用値の移行と再利用を、使う側までつなぐ

保存済みの採用値を再利用・移行する場合は、新規出力に課す条件と、過去の採用を確かめる条件を分けよ。新規 AI 出力の件数上限や根拠分類を、集約済みの保存値へ課して切り捨てるな。
移行対象は最終状態の分類名ではなく、旧処理が判断材料として使った値から決めよ。AI の直接出力に加え、それを規則へ通して得た値や下流の関係も対応付けよ。候補が保存されているだけで採用済みとせず、新しい採用や明示的な取消を古い候補で上書きするな。

処理を省く分岐の return や continue では、生成だけを省くのか、結果の適用まで省くのかを区別せよ。保持したオブジェクトも、後続の引数や集約配列に入らなければ使われない。
AI だけを呼ばない分岐と処理対象から外れる分岐の両方で、採用値が通常の適用処理を経て、グラフや通知などの利用先へ届くか確かめよ。生成結果がないことを、関係なしや取消と解釈させるな。復元時の信頼度や派生値も通常の計算処理に通せ。
保持か取消かは項目全体の成功・延期ではなく、要素ごとの必要性、新しい採用、確定情報による不要化から決めよ。例えば項目全体が延期でも、終了済みという確定情報で不要になった待ち相手を復活させるな。

過去の判定を AI へ固定値として渡す場合は、保存する値と根拠を保ち、今回の入力に必要な情報だけを投影せよ。過去の根拠が今回の取得範囲にないことだけを理由に再利用を止めたり、無関係な再取得・再推論を増やしたりするな。呼び出し不要と決まる前の入力準備に、新規生成専用の条件が残っていないかも追え。

## ビルドと環境変数の変更を、導入理由と後続の利用側から判断する

権限復旧や空ディレクトリ作成のような補助処理を移す・消す場合は、元々何が失われるために必要だったかと、その受け渡し工程が今も通るかを追え。採用版の配布物に必要な権限やディレクトリがあり、展開・改名などを経ても保たれ、後続の受け渡しで再び失われないことを対応付けよ。
「昔からある」や最新版の説明だけで残す・消すを決めるな。アプリ本体と別途取得する同梱物のように生成・配置経路が異なる対象は、対象ごとに判断せよ。
実行ファイル名を使う場合は、表示用製品名・パッケージ名・OS 別の実行ファイル名の生成元を照合せよ。CI の明示設定でたまたま同じ値になることを保証とみなさず、未指定時の実ファイル名とも一致するか確かめよ。

環境変数から動作可否を独自に判定している場合は、採用版の標準処理へ任せられるか調べよ。代わりの判定関数は、公開範囲・判定対象・必要な初期化の時点を確かめてから使え。過去の無効化設定を外す場合は、導入時の回避対象と現在の既定動作、ローカルと CI の差を示せ。
フックの一部の処理だけがモード固有なら、フックは登録したまま該当処理の直前で分岐する案を基準にし、フック全体の契約をモード固有にするな。

環境変数の既定値や必須条件を変える場合は、workflow・job・step の定義と引き継ぎを調べ、初回ビルド、同梱しない構成、後続の再パッケージで実際に渡る値を照合せよ。処理本体を省く経路でも、設定ファイルの読込時に検証されないか確かめよ。
後続 step で空文字に上書きしたくなったら、共通定義を残す前提を疑い、必要な step だけに渡す案と比べよ。既定値や設定範囲を変えてよいと決まったら、補完処理だけでなく入力元も揃え、不要になった回避策を消せ。
環境変数の受け渡しや cleanup を変える場合は、未指定と空文字の違いと、後続がその値を読む条件を確かめよ。直接 env へ渡す経路と、`GITHUB_ENV` のような行単位の形式を経る経路を区別し、ダミー値を実際の受け渡し経路に通して保持と後片付けを確かめよ。

成果物の配置を共通処理へ移す場合は、CI とローカルの各経路で、変更前後の配置先と、起動側が解釈する相対パスの基準を対応付けよ。一経路だけ変わるならその条件を示し、「保存先は変わらない」と全体へ広げるな。
経路ごとに配置先が違う場合は、参照する設定と導入時の議論を確かめ、残ったコードだけから正しい配置を決めるな。変更されなかった事実と、残した意図が記録されていることは別物である。

## 設定の順序は、選択と呼び出しの両方から決める

複数のプラグインが同じ処理の入口を提供し、設定順を変える場合は、どの入口が選ばれるかと、選ばれた実装が他のどの処理を呼ぶかを、採用版の実装で別々に追え。「後のものが選ばれる」で調査を終えず、逆の組合せでも必要な処理が呼ばれるか確かめよ。
各プラグインが自分を最後に置くよう説明していても、その配置を無関係な入口を提供するプラグインまで含む恒久的な制約へ広げるな。別の実装が必要な処理をまとめて呼ぶようになれば、順序を見直す条件になる。

整形プラグインの順序を直したら、問題の整列と併用する整列の両方が必要な未整形の入力で、既存の実行経路から実際の出力を確かめよ。整列処理が呼ばれない設定でもチェックは成功しうるため、終了コードだけで有効化を判断するな。

## コメントと文書には、制約が必要になる理由を判断箇所に残す

ネストした処理へのコメントは、関数全体・条件ブロック・個別命令のどれを説明するか決め、その開始位置に置け。上位で書いた時点や条件は下位で繰り返さず、固有の動作だけを書け。

コードから読み取れない配置や設定の制約は、守りたい結果と、その配置が必要になる処理の関係を書け。「互換性を保つため」のような目的だけでも、「最後のパーサーが選ばれるため」のような選択の仕組みだけでも足りない。なぜその実装に任せるのかを、実際に呼ばれる処理に結び付けよ。
現在の項目名や配置の繰り返しを理由にせず、併用相手や呼び出し関係が変わったときに見直せる説明にせよ。
外部ライブラリが特殊な文字列を制御値として解釈する行には、リテラル・解釈するライブラリ・結果を結び付けて書け。
特定ファイルの配置理由は、ファイル名やパスの繰り返しではなく、「実行ファイル配置領域にテキストファイルを置くと署名に失敗する」のように、制約を生むファイルの種類と領域の関係で示せ。確かめた領域での失敗を、他の配置先すべてへ広げるな。

理由を短いコメントにまとめるときは、調査で使った内部用語を残さず、対象の実装が何を実行するかを動詞で示せ。
条件分岐と呼び出し全体へのコメントでは、制限する条件の理由だけでなく、その処理が実現する利用者の目的を主旨にせよ。
行数の異なる案を求められたら、目的・現在の制約・見直し条件の優先順位で各案に残す情報を選び、同じ情報を長い一行へ詰め込むな。利用者が選んだ情報量を採用し、未採用の説明を後から足すな。
意味が伝わったかは、専門用語の言い換えや文章 lint の通過ではなく、周辺コードとコメントだけを読んで、何を任せ、そのためにどう配置するのかがつながるかで確かめよ。

コメントを書ける設定ファイルでは、項目の順序や値を守る理由を、設定を変える人が読む該当箇所に置き、README の一般的な手順へ分離するな。一項目だけにかかる短いコメントは、直前の独立行だと以降すべての説明に見える場合、該当項目の行末に置け。

実装の背景を説明する文書では、各段落の主旨の理解に必要な事実と因果関係を本文に残せ。条件分岐や版ごとの詳細、別環境の測定が主旨を埋もれさせるなら、経緯や根拠資料へ移して参照できるようにせよ。主旨にも後の判断にも要らない補足は消し、調査で得た情報を本文へ列挙するな。
