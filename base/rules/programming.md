## コーディング規約

- 最初に実装計画を考えよ
  - 実装は実装計画を参照しながら仕様を満たすように行え
  - 実際にコードを書く前に既存コードやドキュメントを熟読せよ
  - 実装にあいまいな点があれば計画に戻れ
- 想定外の挙動は例外を投げよ
  - 余計なフォールバックはバグになるため書くな
  - 型を合わせるために if を使う場合も例外を投げよ
  - どうしてもフォールバックが必要な場合はログを出せ
- エラーを握りつぶすな
  - エラーは問題の早期発見に繋がる
  - catch 内で何もしないのは禁止
  - 到達不能コードは UnreachableError を投げよ
  - null/undefined の排除には assertNonNullable を使え
- 受け取る側が使わないのにエラーを変換するな
  - 変換してよいのは、呼び出し側が種別で分岐する・リトライ判定に使うなど、エラーハンドリングに実際に使うときだけ
  - 型を足したり説明を足すだけの変換はただの冗長
- 別のエラーを投げるときは元のエラーを繋げよ
  - TypeScript は `cause`、Python は `raise ... from` を使え
- 未処理エラーはエラーバウンダリまで伝播させよ
  - エラーバウンダリはロギングのみにせよ
  - リトライやダイアログ表示などで適切に処理した場合は伝播不要
- エラーバウンダリは既にあるものを使え、自作するな
  - CLI・スクリプトは未捕捉例外の出力機構、Web フロントは Error Boundary、サーバーはフレームワークの例外ハンドラが既にそれ
  - 自作するとスタックトレースが失われて調査できなくなる
- もう一度実行して成功しうる失敗は数回までリトライせよ
  - 判断できない失敗はリトライしてよい
  - 要求そのものが誤っている場合など、必ず同じ失敗になるものはリトライするな
  - やり直しで副作用が二重に起きるものはリトライするな
  - リトライの範囲は失敗する操作だけに絞れ
- エラーメッセージの文字列でエラー種別を判別するな
  - エラー判別したい場合はエラークラスを定義せよ
  - エラー判別しない場合はエラークラスを定義するな
- コード内コメントは明確な指示がない限り増やすな＆減らすな
  - コメントは可読性を下げてしまうため書くな
  - 変数名や関数名からわかるコメントを書くな
  - 実装の詳細や処理内容を説明するコメントを書くな
  - public な関数やクラスは docstring を１行書け
  - コメントが必要なら関数に切り出せ
  - もしコードから絶対に意図が読み取れない重要なコメントは必ず書け
  - 明らかに不要になったコメントは削除せよ
- 後回しにすべきものは `// TODO:` を書いて先送りにしてよい
  - 適当な仮実装よりも TODO の方が良い場合に限る
  - セッション内での解決は必須ではない
- 今後も守るべき方針は、実装を変えるだけで終わらせず文章にも残せ
  - 一時的な変更やその場限りの対応は残すな
  - 既に書かれているなら、実装が違反していたと報告せよ
  - 倣える既存の記述がどこにも無いなら書くな
- 変更前のコードやドキュメントと互換性を持たせるな
  - 今最も良いコードが最も良い
  - 最新のドキュメントが最も有用
  - 変更前のことをドキュメントに書くな
- 関数名と振る舞いを一致させよ
  - 名前に収まらないなら関数を分けよ
- 不要は削除せよ
  - 不使用な引数は省け
- 変数・定数は最小スコープで定義せよ
  - 関数内でしか使わないなら関数内で定義せよ
- 統一せよ
  - 関心事が同じ似たコードは近くに配置せよ
  - 変数定義や引数定義の順番を揃えよ
  - 命名規則を一貫させよ
  - 関数名・クラス名と docstring の説明は名詞・動詞を一致させよ
  - docstring 内の用語や文面を統一せよ
  - 関数分け・クラス分けの粒度を揃えよ
- 関数の引数にデフォルト値を与えるな
  - デフォルト値はメンテナンス性を下げる
- 関数の引数・返り値には型を付けよ
- null・undefined・None・0・-1・空文字に別の意味を持たせるな
  - センチネル値を使うな
  - 例外的な値は発見しづらいバグの原因になる
  - 例外的な動作をする値にはシンボルやリテラル文字列を使え
- boolean 以外の値で truthy/falsy チェックするな
  - boolean は `if (flag)` のように直接使え
  - それ以外は厳密比較を使え
- 必要以上に広い型を使うな
  - オプショナルやNullableは不要なことが多い、必要な場合のみ使用せよ
  - 来ないはずの値を救済するロジックは書くな、型を制限しろ
- 型エラーの解決には慎重になれ
  - あなたにはとりあえず型を合わせて辻褄を合わせる悪癖がある
  - 型エラーが起こる本質を把握し、構造から解決せよ
- 三項演算子はネストするな
- API keys や credentials を読むな

## AI エージェント向けアドバイス

- コーディング中のフォーマットエラーは無視しても良い
  - コミットする直前にフォーマッターを使え
- あなたはコード変更によって最後の行に改行を追加することができないことがある
  - 最後の行に改行が無いと静的解析ツールがエラーを出す場合は、フォーマッターを使え
- 指示がない限り git コマンドを実行するな
  - 指示があった場合は許可を求めるな
- 提案するときや、必要か理由を聞かれたときは、次の5段階のどれかを理由とともに明示せよ
  - 理由があって必須
  - 理由があってそうすべき
  - 理由はあるがどちらでも良い
  - 理由はなくそう思っただけ
  - そうしない方が良い
